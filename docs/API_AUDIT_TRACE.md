## 二、请求级审计（api_runtime_events）

### 2.1 事件流与时机

```text
网关统一引擎（jiuzhang_guard 请求链 serveNext 唯一挂点）
  ▼ emitAPIEvent（apiprotect.go:385）→ JSONL 文件 api-runtime-events.log
采集器 Collector（断点续传/轮转/错误文件；2s 周期）
  ▼ SavePrimary（apiruntime/events.go:28）
api_runtime_events（request_id 幂等：同一 Request ID 只生成一个主事件）
```

事件输出时机（apiprotect.go 头注释与 emitAPIEvent 实现）：

| 请求类别 | 输出时机 | response_status 语义 |
|----------|----------|----------------------|
| 阻断类（BLOCK/RATE_LIMIT/TEMP_BLOCK） | 阻断时输出 | 按决策映射 403/429 |
| API 放行流量 | **下游响应完成后输出** | 真实回包状态码 + 真实 latency_ms（入口到响应完成） |
| 非 API 命中（有检测明细的非 API 流量） | 响应前输出（既有行为） | 0 = 未采集 |
| 纯 ALLOW 无明细 | 不落主事件表（notable 过滤，collector.go:91） | — |

响应后输出是 API 安全补全第一批的关键修复：此前放行请求在上游响应前输出事件，
状态码恒 0，学习样本的 response_status 过滤规则无原料；现 API 流量事件携带真实
状态码、时延与响应侧 findings（响应相位明细随同一主事件输出）。

### 2.2 审计列（迁移 000035 新增六列）

| 列 | 语义 | 来源 |
|----|------|------|
| `client_ip` | 真实客户端 IP（guard 入口已改写 RemoteAddr；空 = 不可得） | 网关事件 client_ip |
| `method` | 请求方法（冗余自 endpoint_key 前缀，便于按方法过滤/聚合） | 解析产物 |
| `raw_path` | 归一化前原始路径（不含 query，Emit 时封顶 512 字符） | 解析产物 |
| `latency_ms` | 请求处理耗时（毫秒） | 响应后输出计时 |
| `model_version` | 判定所用 FORMAL 模型版本号（发布通道 api_formal_model_versions 按API下发，网关随事件回报） | 发布通道 |
| `policy_version` | 判定所运行 API 策略版本戳（发布通道 api_policy_version：冻结模型+确认约束+脱敏规则的规范序列化 sha256） | 发布通道 |

落库纪律（events.go:41-66）：六列全部可空；旧版网关事件缺字段时为零值，
空串/非正耗时统一落 NULL——**不伪造 0 值审计数据**（latency_ms=0 视为未上报而非
真实 0 毫秒）。列表接口 `GET /api/v1/api-security/runtime/events`
（api_runtime.read）返回全部审计列，并支持 identity_fingerprint 精确过滤。

### 2.3 覆盖面的如实说明

请求级审计仍是"值得注意"子集而非全量：notable 判定（有检测明细或动作非 ALLOW）
之外的纯通行 API 请求只喂API发现与流量趋势桶，不落主事件表。全量访问日志
（access_logs，000023）须显式启用才覆盖全量请求；当前访问日志与 API 事件已携带
`request_id`，并可共享 `trace_id`。API 运行时事件的 Trace 持久化见迁移 000217。

## 三、操作审计哈希链

管理面操作审计（`audits/audits.go`，阶段2 起闭环）：

- **哈希链**：每条记录计算 `record_hash`（含上一条 `previous_hash`），
  `VerifyChain` 可全量校验链完整性；
- **禁改删**：数据库层 RULE 禁止 UPDATE/DELETE（迁移 000001）；
- **脱敏**：before/after 摘要经 `MaskSensitiveJSON`（口令、密钥、令牌等敏感键
  值替换为掩码）；
- **导出**：审计导出走既有导出链路。

API 安全域已接入操作审计的动作（示例）：模型生命周期（候选/评审/确认/激活/回滚）、
弱点处置（confirm/assign/fixed/retest/ignore/archive，module=api_security，
object_type=api_weakness）、敏感数据类型与脱敏规则管理（apidata）、
学习达标自动完成（learning_auto_complete，actor=system）、策略模式变更与发布。
风险处置（findings 七态状态机八条接口）已按同一纪律接入操作审计
（`apisecurity/risk_handler.go` recordAudit，object_type=api_runtime_finding）。

## 四、主体审计（Identity 单维现状）

- 事件级主体：`identity_fingerprint`（仅凭据派生，匿名为空）+ `auth_type` +
  `source_fingerprint`（客户端 IP 的加盐指纹；迁移 000029）；
- 风险级主体：findings 物化时提取 `subject_type/subject_id`
  （IDENTITY=身份指纹 / IP=来源指纹；永不落明文，findings.go:112）；
- 画像级主体：`api_identity_profiles`（指纹 × API聚合，质量分与风险评估，
  见 docs/API_IDENTITY_AUTHORIZATION.md 第四节）。

现状为 **Identity 单维主体审计**：无应用/租户/角色维度的主体审计视图，
任务书 §86 的多维主体审计为后续迭代项。

## 六、溯源链现状与断点

### 6.1 已通段

```text
Event（api_runtime_events，request_id 幂等）
  ├─→ Finding（api_runtime_findings；采集器物化，request_id 关联首次命中）
  │     └─→ Weakness（api_weaknesses；Sweeper 派生，只读不回写）
  ├─→ ModelVersion（model_version 列直答"命中时生效哪版模型"；
  │     schema 违例另经 api_schema_violations.model_version_id 精确关联）
  ├─→ RuntimePolicy（policy_version 列 = 发布内容哈希，可比对发布记录；
  │     API级策略版本状态机见 api_runtime_policies，迁移 000037）
  ├─→ Identity（identity_fingerprint → api_identity_profiles 画像与风险详情）
  └─→ 操作审计（request_id 贯穿管理面操作审计记录）
```

### 6.2 断点（如实标注）

1. **Coraza 阻断不归因**：guard 先于 coraza 执行，Coraza 独立 403 的请求其
   api_runtime_events 记录（若已产出）的 final_action/response_status 不反映
   WAF 阻断；管理面仅经 x-request-id 事后关联 security_events（P0-08 未实现，
   禁止形态仍是现状）；
2. **纯 ALLOW 无 API 主事件记录**：需显式启用并查询 access_logs；访问日志与 API 域
   已可通过 request_id / trace_id 关联，不再是没有关联键的断点；
3. **Event→Object 无对象维度列**：对象标识只在事件证据扩展中，无独立列可聚合；
4. **Event→SensitiveData 已有运行时字段证据**：details_json 保存单次字段明细，
   api_sensitive_fields 为接口级聚合；数据流图可按 Trace、端点和应用关联真实贡献，
   但尚未形成统一请求审计视图；
5. **主体审计单维**：见第四节；
6. **未实现项**：统一数据审计视图（任务书 §87）、请求审计流向图（§90）、离线审计
   任务（§91）及请求级 PCAP 长期留存。现有 Agent 系统间数据流图不等于请求审计流向图。

## 七、关键设计决策

1. **响应后输出优先于字段完备**：API 放行流量事件延迟到响应完成后输出，
   换取真实状态码/时延/响应侧 findings；阻断类保持即时输出（审计时延敏感场景
   本就已被拒绝，无响应可等）；
2. **NULL 优于 0**：旧版网关缺字段一律落 NULL，宁可"未知"不可"伪造准确值"；
3. **幂等先行**：request_id 幂等 + dedup_fingerprint 幂等，采集器重放/重复上报
   静默去重而非产生重复审计行；
4. **明文最小开口**：全链只开 client_ip 一个明文审计列，其余一律指纹/摘要；
5. **审计写入不阻断业务**：事件输出、findings 物化失败仅告警，不影响请求主流程
   （与采集器既有纪律一致；操作审计则为管理面同步链路，失败如实返回）。

## 九、请求审计、审计流向与 PCAP 冷热分层一体化实施方案（待实施）

### 9.1 文档性质与目标

本节是目标实施方案，不代表以下功能已经上线。它把日志检索与趋势、审计流向图、
单次请求详情和 PCAP 证据合并为同一套请求审计能力，避免分别建设后无法互相关联。

已有基础包括：访问日志及脱敏头体、`request_id` / `trace_id` / `span_id` / `ttfb_ms`、
API 运行时事件、敏感字段、Agent 系统间调用图、Kafka/ClickHouse 观测链和网络诊断
PCAP 工具。现有诊断抓包不是持续生产取证能力，现有系统间数据流图也不等于本节的
请求审计流向图。

目标如下：

1. 任意已采集请求可从日志进入详情、命中规则、敏感字段、Trace 和 PCAP 证据；
2. 日志、趋势和图聚合不读取 PCAP 文件正文；
3. 支持 SSD 热缓冲、SAS 温数据证据库和可选的独立冷归档；
4. 原始 PCAP 与普通脱敏日志分权、分存储、分审计；
5. 无身份、无 Trace、无抓包或关联歧义时明确展示，不补造事实；
6. 抓包、落盘、关联、迁移、核验和下载不得阻断 WAF 业务。

本期不提供 PCAP 或 HTTP 重放，不增加对生产源站主动回注流量的能力。

### 9.2 统一证据模型

一次业务请求使用以下标识，不允许混用：

| 标识 | 用途 | 限制 |
|------|------|------|
| `request_id` | 请求审计主键，连接日志、运行事件、敏感字段和 PCAP 关联记录 | 不信任客户端伪造值；管理面自身请求 ID 与被调查请求 ID 分开 |
| `trace_id` / `span_id` | 关联真实 Agent CLIENT/SERVER 调用和 APM | 不作为 PCAP 包内天然存在的标识 |
| `connection_evidence_id` | 标识节点、接口、连接纪元和五元组对应的抓包证据 | 连接复用时需保留覆盖范围，不能冒充单请求独占 |
| `artifact_id` | 一个不可变 PCAP 分片的服务端生成 ID | 不使用用户文件名或任意路径作为主键 |
| `evidence_version` | 关联策略、采集器、生成器和清单格式的版本 | 便于重放采集器重算时保持幂等，不用于业务流量重放 |

证据结论拆成三个正交维度：

- 捕获：`PENDING` / `READY` / `INCOMPLETE` / `NOT_CAPTURED` / `EXPIRED` / `UNAVAILABLE`；
- 关联：`PENDING` / `MATCHED` / `AMBIGUOUS` / `UNMATCHED` / `FAILED`；
- 完整性：`UNVERIFIED` / `PASS` / `FAILED` / `KEY_UNAVAILABLE`。

`NOT_CAPTURED` 必须携带 `POLICY_DISABLED`、`OUT_OF_SCOPE`、`QUEUE_FULL`、
`CAPACITY_EXCEEDED`、`IO_PRESSURE`、`KEY_UNAVAILABLE`、`CAPTURE_ERROR` 等原因。
只有 `READY + MATCHED + PASS` 才能按正常请求证据导出；其余状态必须给出明确原因。

### 9.3 总体数据流

```text
客户端 → Caddy / jiuzhang_guard → 源站
             │
             ├─ 访问日志 / API运行事件 / 脱敏字段与命中规则
             │       → 现有采集器 → PostgreSQL（权威请求记录）
             │                         │
             │                         └─ 可选大流量读模型：事务Outbox → Kafka → ClickHouse
             │
             ├─ 小型非阻塞取证触发（仅ID、节点、时间和策略版本）
             │
             └─ 独立抓包进程 → 有界内存队列 → SSD热分片
                                                   │ 封口/加密/哈希/清单
                                                   ▼
                                             SAS不可变温分片
                                                   │
                                                   └─ 可选独立冷归档

请求详情 / 趋势 / 审计流向图 → 只读结构化元数据与索引
PCAP核验 / 派生导出           → 按索引读取指定分片，不扫描全盘
```

约束如下：

- PCAP 正文不进入 PostgreSQL、ClickHouse、Kafka、Observation、Syslog 或普通操作审计；
- WAF 热路径不等待 PCAP 的磁盘写入、`fsync`、加密、关联、数据库或下载；
- PostgreSQL 保留权威请求记录；大流量读模型不可用时不得把过期缓存冒充最新结果；
- 系统间 A→B→C 的字段证据继续使用真实 Agent Trace，不能从 PCAP 流量相似度推断；
- 原有 Caddy 中间件顺序不因 PCAP 改变。

### 9.4 日志检索、趋势和导出

#### 筛选维度

统一请求审计列表至少支持：

- 时间范围、节点、应用、域名、请求方法、规范化 API；
- 客户端 IP、账号/身份指纹、设备标识（仅已有可靠来源时）；
- 命中规则 ID、规则类型、风险级别、处理结果、响应状态码；
- 请求 ID、Trace ID、是否含敏感字段、PCAP 捕获及关联状态。

时间采用左闭右开区间。应用和权限过滤必须由服务端执行，前端隐藏条件不视为授权。
API 查询默认使用规范化路径，不把原始查询串中的敏感值作为展示字段。

#### 大流量查询路径

基础规模可继续使用有索引的 PostgreSQL 访问日志。目标规模证明 PostgreSQL 不足时，
启用 ClickHouse `request_facts` 读模型，而不是在每次查询时扫描全量日志：

- 请求事实以 `(gateway_node_id, request_id)` 幂等；
- 敏感字段、规则标签使用有界数组或独立事实表；
- 趋势按分钟、小时、天预聚合；有筛选的趋势在限定时间窗内查询请求事实；
- 列表采用稳定排序和游标分页，避免深分页反复扫描大 offset；
- 大结果导出使用有界异步任务，记录筛选快照、行数、创建人和过期时间；
- 读模型存在延迟时展示最后同步水位，不以旧数据冒充当前完整结果。

如果采用 Outbox，请求记录与 Outbox 必须在同一 PostgreSQL 事务中提交；由独立发布器
送往 Kafka。禁止业务代码先写 PG 再各自无保障地双写 Kafka/CH。

#### 趋势口径

趋势至少区分请求数、阻断数、风险请求数、涉敏请求数和响应错误数。请求数按去重后的
`request_id` 计算，不把一次请求中多个字段或多个规则重复计为多次请求。

### 9.5 审计流向图

审计流向图是请求审计的聚合视角，与已有系统间调用图分开呈现：

```text
来源IP / 已验证账号
        │
        ├─ 请求敏感字段（side=REQUEST）
        │
        ▼
      应用 → API
        │
        └─ 响应敏感字段（side=RESPONSE）
```

实现规则：

1. 节点类型：来源、账号、请求字段、应用、API、响应字段；支持按类型显示或隐藏；
2. 边计数默认使用去重请求数，同时保留字段命中数，二者不能混用；
3. 请求字段与响应字段分开，响应字段不表示一次反向 API 调用；
4. 无账号时进入“匿名/未识别”或按配置不生成账号节点，不从任意参数猜测账号；
5. 字段节点包含真实 `path + data_type`，不包含字段原值；
6. 节点和边支持下钻到请求列表及单次证据；聚合计数必须能还原到同一筛选集合；
7. 大结果使用 Top N 加分页或“其他”桶，“其他”桶保留真实数量，不伪造详情；
8. 节点类型开关只改变显示，不修改底层事实与统计口径；
9. PCAP 只作为符合条件的请求证据入口，不为画图扫描 SAS 或解析 PCAP 正文。

已有 `view=service` 的系统间 A→B→C 图继续只使用真实配对 Observation。只有证据记录
明确暴露请求标识且 PCAP 关联唯一时，才允许从该证据跳转 PCAP；不得把系统级字段
汇总误标为单次请求包证据。

### 9.6 单次请求详情

在现有访问日志详情中提供统一视图，不新增一级菜单：

| 区域 | 内容 |
|------|------|
| 摘要 | 时间、节点、应用、域名、方法、规范化API、客户端IP、状态、处理结果、请求ID |
| HTTP证据 | 已脱敏的请求/响应头和正文、截断状态、Content-Type、字节数；未采集显示未采集 |
| 规则与字段 | 命中规则、风险、请求/响应敏感字段路径与类型、模型和策略版本 |
| Trace | Trace/Span、真实上下游、证据类型、样本关联质量 |
| 性能 | 请求总耗时、实际采集的上游首字节与完成时间、各阶段真实耗时 |
| PCAP证据 | 捕获、关联、完整性状态，覆盖范围、包数、丢包/截断、到期时间、核验和下载入口 |

性能口径必须真实：已有 `duration_ms`、`ttfb_ms` 可展示原值，但不能用
`duration_ms - ttfb_ms` 冒充 WDSP 自身处理耗时。需要拆分客户端、WDSP 和源站阶段时，
必须在相应边界新增真实时间戳；未采集的阶段显示“未采集”。

普通详情不返回原始密码、Cookie、Token 或完整业务报文。原始 PCAP 的下载权限不能由
普通日志查看权限推导。

### 9.7 PCAP 捕获范围与留存模式

#### 捕获点

| 捕获点 | 能观察到的内容 | 主要边界 |
|--------|----------------|----------|
| WAF 本机入口/出口 | 客户端到网关、网关到源站的实际包 | 需要本机抓包权限；TLS入口包仍是密文 |
| 交换机镜像/SPAN | 不侵入代理链的网络流量 | 镜像丢失、NAT、加密和多节点归属需单独处理 |
| 业务节点 Agent | 业务节点收发包及本地连接元数据 | 不能远程传输原始PCAP到既有Observation通道 |

HTTPS 经 WDSP 终止后可在线识别 HTTP 字段，不代表历史 PCAP 可以恢复明文。不得保存
TLS 私钥或会话密钥作为默认取证方案，也不得把 HTTP 日志重新封装后冒充原始 PCAP。

#### 两种模式

- `FULL`：对策略覆盖的节点、站点、端口持续抓取，不主动抽样；完整性仍受内核丢包、
  截断和资源故障影响，所有缺口必须入清单；
- `EVIDENCE`：保留有界滚动热缓冲，出现阻断、涉敏、越权等触发时封存事件前后窗口。
  未触发长期留存的普通流量可淘汰，界面不得标为全量长期留存。

推荐初始组合为“FULL 短期热保留 + EVIDENCE 长期温保留”。合规要求全部长期留存时，
必须切换为明确的 FULL 长期策略并完成容量验收。

滚动缓冲只能覆盖尚未承诺长期保留的数据；已封口且未到期的证据不得因空间不足被静默
覆盖。容量满时停止新取证并记录 `CAPACITY_EXCEEDED`，不能伪装成正常到期。

#### 分片格式

- 每抓包点、接口和链路类型使用独立分片，避免混用无法识别的链路头；
- 初始候选参数为 `256 MiB` 或 `60 秒` 封口，最终由目标硬件压测决定；
- 使用经典 PCAP 时保留每包原始时间戳和16字节记录头；`snaplen` 截断必须显式记录；
- 当前诊断解析器仅支持部分经典 PCAP，若选 PCAPNG 或新链路类型必须同步实现并测试，
  不得靠文件名宣称支持；
- 分片内存、打开文件数、写入时间和队列字节数均有硬上限；
- 正在写入、封口、迁移中的分片不可作为完整证据下载。

### 9.8 请求与 PCAP 的可靠关联

关联服务综合使用节点、抓包接口、五元组、连接开始纪元、连接/流标识、请求顺序、
时间和 Trace 元数据。不能只用四元组和时间相近就输出 `MATCHED`。

至少处理以下情况：

1. HTTP/1.1 连接复用：保留请求在连接内的顺序和证据覆盖范围；
2. HTTP/2、QUIC：共享连接且无法精确选包时标为连接级证据或 `AMBIGUOUS`；
3. NAT、代理和节点漂移：使用实际观测点身份，不把代理地址冒充终端；
4. 同 Trace 多接口：字段和 PCAP 不得仅凭 Trace 传播到其他接口；
5. 重复或乱序事件：按稳定键幂等关联，超过关联水位后转为 `UNMATCHED`，而非永久等待；
6. 丢包、截断或抓包进程重启：标为 `INCOMPLETE`，不得输出完整证据结论。

导出共享分片前必须按可靠包范围生成派生 PCAP。派生清单记录原分片 ID、原哈希、
选包范围、派生哈希、生成器版本和覆盖级别。不能精确隔离时，第一期不开放“请求专属
PCAP”下载；连接级导出也需独立授权并明确可能包含同连接的其他请求。

### 9.9 SSD / SAS 冷热数据分层

| 层级 | 内容 | 关键约束 |
|------|------|----------|
| 内存 | 有界抓包队列、事件前滚动窗口、当前块缓冲 | 不允许以内存无限增长换取不丢包 |
| SSD专用区 | 当前加密分片、短期热分片、有界迁移队列、PG/WAL、CH热索引、Kafka临时队列 | 独立挂载或硬配额，禁止写满系统根分区 |
| SAS数据盘 | 已封口加密PCAP、温数据清单和校验信息 | 大分片顺序写；不承担每请求小文件或热数据库 |
| 可选冷归档 | 有独立保管要求的长期证据 | 不直接承接实时抓包；需恢复和完整性验收 |

冷热迁移同时受时间和容量控制：`hot_max_age`、`hot_max_bytes`、`warm_retention_days`、
`warm_max_bytes`。PCAP、请求元数据、字段索引和趋势聚合分别配置保留期，但详情必须能
说明“日志已过期/PCAP仍存在”或“PCAP已到期/日志仍存在”。

正在写入的热分片也采用流式加密，不在 SSD 留下明文临时 PCAP。每个分片使用独立随机
DEK，密钥包裹和历史 `key_id` 由管理面受控保存；抓包节点不持有长期主密钥。

迁移顺序固定为：

```text
SSD封口 → SAS临时对象 → flush/fsync → 大小及SHA-256复核
        → 持久化SAS清单并标记WARM → 删除SSD热副本
```

任何一步失败都保留可恢复状态，不允许先删热副本再确认温副本。到期采用
`ACTIVE → EXPIRING → EXPIRED`，中途崩溃可恢复；异常丢文件是 `UNAVAILABLE`，不是正常到期。

### 9.10 容量与性能计算

#### PCAP 日增长

经典 PCAP 可按下式估算：

```text
R_pcap ≈ PPS ×（平均实际捕获帧字节数 + 16字节记录头）
日增容量 = R_pcap × 86400 ÷ 实测压缩比
规划容量 = 日增容量 × 保留天数 ÷ 目标利用率
           + 索引/清单/加密块/未封口分片/派生导出余量
```

PPS 和平均帧长必须包含双方向真实包分布、握手、ACK、重传、筛选、抓包截断及节点数。
多抓包点重复覆盖不能重复误算为唯一业务证据，但物理容量必须按实际保存副本计算。
TLS 密文和压缩内容不得预设高压缩比。

仅作估算示例：1000请求/秒、请求与响应应用数据合计16KiB、假设PCAP放大系数1.5且
不计算压缩收益，则约为24.6MB/s、2.12TB/日、14.9TB/7日。该示例不是性能实测，也不
可代替真实 PPS 和包长分布。

千兆链路满速仅按 `1Gbps ÷ 8` 粗估为125MB/s、10.8TB/日，尚未充分计入记录头、
余量和导出读取。大流量 FULL 长期留存不能直接按普通业务日志容量采购。

#### SSD 热区

```text
SSD热区下限 ≈ 峰值PCAP字节率 × 热保留秒数
              + 当前分片 + 有界迁移积压 + 导出余量
```

还需保留足够空闲空间避免 SSD 写放大和垃圾回收导致尾延迟。SSD 只吸收突发；如果平均
增长率长期高于 SAS 迁移能力，热区最终仍会耗尽。

#### SAS 持续能力

SAS 是接口，不是吞吐保证。必须记录 HDD/SSD、转速、盘数、RAID级别、控制器写缓存、
文件系统、挂载参数及重建状态。规划时以实测混合读写能力为准：

```text
长期PCAP写入 + 在线导出读取 + 完整性核验读取
< 目标SAS实测混合持续能力 × 安全系数
```

建议初期使用不超过实测持续能力约60%作为规划起点，并依据长稳结果调整。集中导出、
到期清理和 RAID 重建不能与高峰写入争抢到影响业务。全 SSD 也仍有写寿命、垃圾回收、
阵列和控制器瓶颈，不能免除实测。

### 9.11 降级、资源隔离与告警

| 故障/压力 | 处理 |
|-----------|------|
| 抓包队列满、CPU过高 | 有界丢弃取证任务并记录原因，WAF请求继续 |
| SSD达到软水位 | 提前迁移、告警；不突破系统盘硬配额 |
| SAS变慢、只读或满盘 | 停止新取证或有界收尾，标记缺口；不删除未到期证据冒充释放成功 |
| 密钥服务不可用 | 不写明文，标 `KEY_UNAVAILABLE`；业务不受影响 |
| PG/CH暂不可用 | 保留既有采集恢复纪律，展示同步水位；不伪造完整查询结果 |
| 抓包/关联进程崩溃 | 恢复到最后完整记录；无法确认的分片标不完整 |
| 完整性校验失败 | 禁止下载并告警，不能继续外发被篡改证据 |
| 下载缓慢或客户端断开 | 有界执行槽、固定缓冲、及时取消，不积累无限任务 |

抓包、迁移、核验、导出分别使用独立资源预算。cgroup 的 CPU、内存、任务数和 IO 限制
需验证实际生效；不支持 IOWeight 的环境应采用可验证的等效限流。每个节点聚合上报告警，
不为每个包或请求生成一条系统告警。

至少监测：内核及用户态丢包、队列字节数、热/温区使用率、待迁移字节数、封口与fsync
时延、关联待处理/歧义数、完整性失败数、下载执行槽、请求读模型水位和 WAF 配对性能。

### 9.12 安全、权限和证据保管链

新增独立权限，不从 `access_logs.read` 或 `network_tools.download` 推导：

- `request_pcap.read`：查看捕获、关联、完整性及非内容清单；
- `request_pcap.download`：申请并执行受控下载；
- `request_pcap.manage`：修改抓包范围、保留期和容量策略；
- `request_pcap.verify`：执行有界完整性核验。

下载和核验要求实时鉴权、操作理由、速率限制和审计；高风险下载可使用二次认证及短时、
单次、绑定用户和会话的授权单。所有授权变化通过现有管理面 CSRF 与权限链处理。

文件安全约束：

- API 只接受 UUID 或授权单 ID，绝不接受任意文件路径；
- 路径由服务端生成，防止路径穿越、符号链接、FIFO 和非普通文件；
- 在同一打开文件描述符上复核身份与哈希，避免校验后文件被替换；
- 派生导出流式解密，不在服务器写明文临时 PCAP；
- 下载响应使用固定 ASCII 文件名、`no-store`、`nosniff` 和附件 Content-Disposition；
- 页面不在线预览原始包载荷，不复用网络诊断的明文 `preview` 字段。

每个分片保存原始 PCAP 哈希、密文哈希、清单哈希、节点与时间、采集策略、软件版本、
包数、截断及丢包计数。清单签名和只追加保管事件用于系统内完整性证明；没有外部可信
时间戳及合规流程时，不宣称已完成司法存证。到期删除不承诺磁盘字节物理不可恢复。

### 9.13 接口与页面边界

建议新增独立、受控的请求审计接口，不复用网络诊断任务接口：

| 接口 | 用途 |
|------|------|
| `GET /api/v1/request-audit/events` | 组合筛选、游标分页、同步水位 |
| `GET /api/v1/request-audit/timeline` | 有界趋势与聚合并发控制 |
| `GET /api/v1/request-audit/flow` | 审计视角节点、边、计数和下钻条件 |
| `GET /api/v1/request-audit/events/{id}` | 单次请求摘要、脱敏证据、Trace、真实耗时和PCAP状态 |
| `GET /api/v1/request-pcap/lookup` | 按业务请求ID查询PCAP三维状态 |
| `GET /api/v1/request-pcap/artifacts/{id}/manifest` | 查看受限清单，不含密钥和内部路径 |
| `POST /api/v1/request-pcap/artifacts/{id}/verify` | 权限校验、创建有界核验任务并审计 |
| `POST /api/v1/request-pcap/artifacts/{id}/download-grants` | 理由、二次认证和单次下载授权 |

页面嵌入现有访问日志、API运行事件和存储页：访问日志提供列表/趋势/审计流向/详情，
存储页仅展示聚合容量和降级状态，网络工具继续承担临时诊断。列表不得为每行单独请求
一次 PCAP 详情；仅在打开详情时查询。

### 9.14 分阶段交付与验收

| 阶段 | 范围 | 出口条件 |
|------|------|----------|
| S0 契约与实测 | 冻结状态、权限、保留策略、协议范围；测量目标SSD/SAS和真实包分布 | 形成容量基线和验收阈值，无实测不得承诺SAS可承受指定流量 |
| S1 请求审计闭环 | 组合筛选、趋势、单请求详情、真实耗时和Trace跳转 | 单元、接口、权限、分页和真实浏览器验收通过 |
| S2 SSD证据闭环 | 独立抓包、加密封口、关联状态、受控派生导出 | 真实Caddy/WAF/源场景及崩溃、丢包、权限测试通过 |
| S3 SAS温层与流向图 | 冷热迁移、保留墓碑、审计流向、存储告警 | 迁移一致性、到期恢复、图证据一致性和SAS实测通过 |
| S4 生产加固 | 多节点、故障注入、性能与长稳、升级回滚 | 目标硬件组合长稳与回滚演练通过后按策略灰度启用 |

每阶段只交付一个可验收闭环，不用 Mock 数据或静态图冒充生产能力。

#### 功能与安全验收

- 放行、阻断、涉敏请求均可从日志进入统一详情；
- 各筛选、趋势、图计数和详情来自同一请求集合，重复事件不重复计数；
- 无账号、无Trace、无PCAP、PCAP过期和关联歧义均显示真实状态；
- 缺少 `request_pcap.read/download` 时直接调用接口仍被拒绝；
- 路径穿越、符号链接、篡改文件、重复使用授权单均拒绝；
- 测试用敏感哨兵不得出现在普通日志、审计、Observation、Kafka或CH中；
- 下载的派生 PCAP 可由独立工具读取并复核哈希，不只依赖项目自身解析器；
- HTTP/2/QUIC、TLS、NAT、多节点和共享连接按实际证据降级，不伪造单请求范围。

#### 故障与性能验收

- 持续业务流量下注入队列满、SAS高时延/只读、配额耗尽、密钥不可用、进程强杀、
  PG/CH暂不可用、迁移中断和下载中断；
- WAF 转发和安全判定不变，不出现无限队列、无界内存或新增非预期5xx；
- 所有未捕获和不完整证据有明确终态与可核对的计数；
- 在目标物理 SSD+SAS 上执行 PCAP OFF/ON 配对压测，覆盖下载、核验、迁移和清理；
- 记录实际 RPS/PPS、包长分布、TLS比例、H1/H2比例、CPU/RSS、丢包、磁盘吞吐、
  IOPS、await、fsync、迁移积压和 WAF P95/P99；
- 初步峰值余量测试不能替代至少72小时的组合长稳；具体业务 SLA 在测试前冻结；
- 达不到容量或时延目标时减少抓包范围、增加盘阵或独立证据存储，不以静默丢包冒充全量。

#### 回滚

功能默认关闭并按节点灰度。回滚停止新取证、保留已加密证据和密钥历史，不自动删除
数据，不改变 guard 中间件顺序。生产已存在证据时不得自动执行破坏性 down 迁移。
至少验证“升级→产生证据→回滚→WAF正常且停止新PCAP→前滚→旧证据仍可核验”。

### 9.15 冻结的主要取舍

1. 业务稳定性优先于取证覆盖率，但所有缺口必须显式记录；
2. 已承诺保留的证据优先于最新流量，容量满时不静默覆盖未到期证据；
3. 严格关联优先于“看起来有数据”，连接复用和加密场景不得猜测请求范围；
4. 大分片加索引优先于每请求小文件，以适应 SAS 顺序写；
5. 元数据查询与 PCAP 内容读取分离，趋势和审计图不扫描证据文件；
6. 原始证据不可通过改写敏感值来同时保持“原始”，因此采用加密、独立授权和有限保留；
7. 系统内完整性保管不冒充司法存证，重放不属于本期范围。
