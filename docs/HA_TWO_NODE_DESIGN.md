# 双节点高可用与数据同步方案（HA Two-Node Design）

> 目标：两台网关节点组成高可用对，配置一致、计数/行为状态共享、任一节点故障不中断防护。
> 基础：当前代码库已具备的关键件（均经测试验证，见 docs/DEVELOPMENT_STATUS.md 阶段8）：
> - 发布扇出（迁移 000074）：同一构建产物推送至全部登记节点（Caddy Admin `/load` + 规范化哈希比对 + 逐节点 `last_sync_*` 回填）
> - 节点心跳（`api_node_heartbeat_seconds`）：单向日志通道上报活性 + 版本戳，无流量也不失活
> - 节点一致性视图（`GET /api-security/nodes[/consistency]`）：版本不一致产告警（CONFIG_HASH_MISMATCH/CONFIG_PUBLISH_FAILED）
> - 共享状态存储：`behavior_store=valkey`（滑窗/游标/并发，Lua 原子、Fail-open）+ CC 计数 `counter_backend=valkey`
> - 采集幂等：事件按 request_id 去重、批次事务原子提交、断点续传
> - 脱敏密钥/身份盐经发布通道全节点一致下发

## 1. 推荐拓扑

### 1.1 转发面：两网关 Active-Active（首选）

```text
                ┌──────── 负载均衡 ────────┐
                │  云LB / 硬件LB / DNS轮询   │  ← 客户端入口（VIP/域名）
                └──────┬───────────┬───────┘
                       ▼           ▼
               网关节点A          网关节点B        （同版本镜像、同一份发布配置）
               │                │
               └──→ 共享 Valkey ←──┘               （行为/限速计数共享：A60+B60>100 成立）
                       │
               管理面（api）+ PostgreSQL 主库       （配置/资产/模型/审计唯一权威）
```

- **负载均衡选择**（按部署环境三选一）：
  1. 云/硬件 LB（最稳）：健康检查 `/health`（Caddy 已提供），故障自动摘除；
  2. Keepalived VRRP VIP（无外部 LB 时）：双机各跑 keepalived，VIP 漂移；注意 gratuitous ARP 与脑裂抑制（仲裁建议加第三观测点或 `nopreempt` 策略按场景选择）；
  3. DNS 轮询（最简）：故障摘除慢（TTL 级），仅建议灰度/实验环境。
- **会话亲和**：不需要。所有共享判定状态（CC/行为/封禁）在 Valkey，任何节点处理任一请求语义一致。身份指纹盐（`identity_salt`）经发布通道全节点一致。

### 1.2 数据面：单写多读

- **PostgreSQL 主库唯一**：两节点的管理面服务连同一主库；高可用增强可选流复制 + 故障切换（Patroni/repmgr）或云托管主备（见 §3）。
- **Valkey 单实例共享**（v1 最简）或主从（v2 增强）：计数类状态允许重建（丢失仅影响窗口期判定，Fail-open 已覆盖故障语义）。
- **网关→管理面单向日志采集**保持不变（架构红线）：每节点各自 `api-runtime-events.log` + 断点，采集器按 request_id 幂等去重；节点重启/断流重放安全。

### 1.3 管理面形态

两节点部署下管理面（api）**单实例即可**（它不承载实时转发，故障期间防护不受影响：网关在最后一次成功发布的配置上继续运行，采集积压由断点幂等追平）。若要求管理面也 HA：双 api 实例共享同一 PG + Valkey，无状态天然可双跑（采集器双跑安全：request_id/幂等键去重，唯一注意点是周期任务的重复执行——见 §4 守护任务幂等说明）。

## 2. 数据同步矩阵（每类数据的机制与一致性级别）

| 数据类 | 同步机制 | 一致性 | 现状 |
|---|---|---|---|
| 站点/防护/策略配置（含 API 模型、约束、脱敏、授权基线、合规规则、签名/扫描密钥） | 发布扇出：一次构建 → 全节点 `/load` + 哈希比对 + 逐节点回填 + 不一致告警 | 强（同一份构建产物） | **已交付** |
| 回滚 | 整站版本快照 + 各节点同机制扇出回滚 | 强 | 已交付（主节点回滚 + 扇出跟随） |
| CC 限速/临时封禁计数 | `counter_backend=valkey` 共享计数器（既有） | 强（共享原子计数） | 已交付（阶段5） |
| 行为滑窗/对象游标/凭据并发与跨 IP 检测 | `behavior_store=valkey` 经发布下发启用 | 强 | 已交付（第一波起可下发；**默认 memory，部署时必须显式置 valkey**） |
| 敏感值规则/角色基线/字段权限/合规规则/LLM 名单 | 随发布扇出（哈希入版本戳） | 强 | 已交付 |
| 运行时事件/审计 | 各节点各自日志卷 → 采集器汇聚入库（request_id 幂等 + 批次事务原子） | 最终一致（秒级） | 已交付（第二十一/二十二波强化） |
| 身份指纹 | 同一 `identity_salt` 经发布下发（Redact 脱敏） | 强 | 已交付 |
| 证书 | 证书管理在管理面（certificates 表+密钥加密），经发布通道分发到节点 | 强（发布驱动） | 已交付（阶段3 起） |
| GeoIP 数据文件 | 各节点本地数据文件，部署物同版本打包（不运行时同步） | 部署一致 | 已交付（runtime/geoip 同版本构建） |
| 模型/策略版本账本 | PG 唯一账本（`api_runtime_policies` 等），网关侧不存状态 | 强 | 已交付 |

## 3. PostgreSQL 与 Valkey 的高可用选项

- **v1（推荐起步）**：PG 主从流复制（异步）+ 备份恢复（既有 backups/restore 体系）；故障时手工/脚本切换。Valkey 主从哨兵或接受单实例+快速重建（计数状态可丢，Fail-open 兜底）。
- **v2（可选增强）**：PG 同步复制或托管主备（云 RDS 类）；Valkey Sentinel 自动切换（网关 counter/behavior 客户端需支持重连——既有实现按连接重试+Fail-open 已覆盖短暂中断）。

## 4. 脑裂与故障处理

- **转发面脑裂不存在**（无共享写状态在两网关之间产生分歧：配置同源、计数共享）；
- **管理面分裂**（双 api 形态时）：周期任务（聚合/学习/弱点派生等）双跑幂等已由设计覆盖（upsert/幂等键/水位同事务）；发布操作建议人为单点纪律或后续加 leader 选举（现状：发布动作是人工触发，风险可接受，如实记录为已知边界）；
- **节点失联**：心跳 STALE（>5min 无事件）/SILENT（>1h）+ 一致性告警；LB 健康检查摘除；恢复后发布扇出+断点续采自动对齐，无需人工干预；
- **数据漂移检测**：`/nodes/consistency` 明确回答全节点版本一致性；不一致自动告警并可一键重发（回滚/重发布接口既有）。

## 5. 部署清单（两节点最小落地）

1. 两台网关主机：同版本镜像（digest 锁定），`api_dynamic_protection=true`、各自 `gateway_node` 唯一名（如 `gw-a`/`gw-b`）、`api_node_heartbeat_seconds=60`；
2. 管理面：登记两节点 `PATCH /api-security/nodes/{id}`（admin_addr=各节点 Caddy Admin 通道、sync_enabled=true）——发布即扇出；
3. 基础设施：共享 Valkey（`counter_backend=valkey` + `gateway_runtime.behavior_store=valkey` 经系统设置下发）、共享 PG 主库、各自本地日志卷；
4. LB/VIP：按 §1.1 三选一；健康检查 `/health`；
5. 告警联动：`API_GATEWAY_NODES` 组件告警（版本不一致/同步失败/节点静默）接入通知渠道（notification-channels 已有）。

## 6. 验证方案（全部可自动化）

> **已落地（2026-08-22）**：编排 `deployment/ha-lab/`（Caddy 前置 LB + 双网关 + 共享 PG/Valkey + nodepatch 身份补丁工具）、验证脚本 `test/ha/ha-lab-verify.sh`（下述 S1-S5 全场景，支持 `--scenario` 单跑）；快速指引见 docs/DEPLOYMENT.md 双节点附录。lab 形态取舍（身份补丁、共享事件总线卷）如实记录在编排文件头注释。
>
> **实测通过（2026-08-22）**：S1-S5 全场景整跑 **28/28 通过**（S3 含 5 分钟 STALE 窗口，整跑约 25 分钟）。实测暴露并已修复一个真实装配缺陷：网关心跳采集接线遗漏——`apiruntime.Collector.SetHeartbeatRecorder` 未在 `server/cmd/api/main.go` 装配层调用，心跳记录已产出已采集但不落 `api_gateway_nodes`，节点活性/版本视图失真（S3 恢复 ACTIVE、S4 漂移/CONFIG_HASH_MISMATCH 均因此失败）；补接线后双节点 ACTIVE、版本哈希一致、告警链路全通。脚本侧三处断言按实测行为修正并留有注释：硬停瞬间在途请求被 LB 直接 502（不进网关管线不产事件，阈值 ≥11/12）、告警引擎同指纹合并不增行（改为清场后断言新建 OPEN 行）、S4 版本标记跨轮残留 ENABLED 导致无版本差（开场幂等复位 DISABLED 并发布收敛基线）。

1. **配置一致性**：发布一次 → `/nodes/consistency` consistent=true；人为改 B 节点本地配置 → 下一轮一致性告警 + 重发恢复；
2. **共享计数**（任务书 §123 场景）：A/B 各打 60 次同身份写请求（阈值 100）→ 共 120>100 触发一次统一限速（需 `behavior_store=valkey`）；
3. **故障摘除**：停 B 节点 → LB 摘除 + 流量全走 A + B 心跳 STALE 告警 → 起 B → 心跳恢复 ACTIVE + 采集追平（断点续传，零丢失零双计）；
4. **发布中故障**：发布瞬间杀 B → A 成功 B 记 FAILED + 告警 → B 恢复后重发对齐；
5. **管理面中断**：停 api 10 分钟（网关持续防护，最近一次配置生效）→ 恢复后事件追平、学习/聚合续跑。
（1/2/4 可接入现有 `server/tests` 与 stage5 编排自动化；3/5 建议纳入交付演练手册 docs/DEPLOYMENT.md 附录。）

## 7. 分阶段实施

- **第一阶段（现状即可达成）**：双网关 Active-Active + 共享 Valkey/PG + 发布扇出 + 心跳/一致性视图——除 LB/VIP 外**全部为已交付能力**，仅需部署编排与验证脚本；
- **第二阶段（运维增强）**：PG 流复制自动切换、Valkey Sentinel、采集器吞吐批量化（已记录的后续方向）、发布 leader 选举（双 api 形态）；
- **不做（如实边界）**：网关间实时状态 gossip（用共享存储替代）、QUIC 层会话迁移、跨地域多活（单地域双节点为本方案范围）。

## 8. 风险与边界（如实声明）

### 8.1 次要节点 Caddy Admin API 暴露面（风险与加固）

- **风险**：发布扇出经次要节点 Caddy Admin API（`/load`）下发配置。该 API **无鉴权**；`admin_addr` 采用 `http://` 时发布载荷明文过网——载荷含身份盐、文件签名/扫描验证密钥、站点证书私钥等密钥材料，同网段监听者即可窃取密钥并获得配置面写入能力（等于接管该节点全部防护策略）。
- **已有防线**：`admin_addr` 登记时仅接受 unix socket 或内网地址（回环/RFC1918/链路本地；主机名全量解析、任一公网/保留地址即拒绝），拨号时 DNS 重解析复检防重绑定（`server/internal/gatewayconfig/caddyclient.go`，`ValidateNodeAdminAddr`/`NewCaddyClientForAdminAddr`）。
- **生产部署纪律**：
  1. 主节点本机 Admin API 保持 Unix Socket、不暴露 TCP（项目红线）；次要节点 http(s) 管理地址为多节点扇出的受控例外（见 AGENTS.md 禁止事项条）；
  2. 生产应使用 `https://`（节点 Admin 端点挂内部 PKI 证书），`http://` 仅限已隔离的带外管理网段；
  3. 次要节点 Admin 端口**绑定管理网卡**，不随业务网卡/转发面暴露；
  4. 防火墙白名单仅放行管理面主机到次要节点 Admin 端口的流量，默认全拒；
  5. ha-lab 形态（admin_addr 登记为共享卷 unix socket 路径、业务端口一律绑 127.0.0.1）仅为单机实验形态；跨机生产部署才涉及 http(s) 管理地址，必须按上述 2-4 条收敛暴露面。

### 8.2 其他边界

- 两节点共享 Valkey 是计数类单点：Valkey 故障时行为/CC 判定 Fail-open 降级（已有测试覆盖），不中断转发；
- 发布扇出"次节点失败不阻断主发布"意味着窗口期两节点可能版本不一致——由一致性告警兜底并支持重发，不构成静默分歧；
- 异步 PG 复制的切换窗口可能丢失最近秒级管理面写入（资产/审计）；安全策略面（配置）无影响（网关在已发布配置上运行）；
- 双 api 实例形态下发布/扫描/学习任务建议人为单点执行纪律（自动 leader 选举列为第二阶段）。
