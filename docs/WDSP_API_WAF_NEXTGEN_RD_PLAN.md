## 1. 研发结论与目标

九章 WDSP 已具备 WAF、API 资产与模型、JWT 信任链、对象授权观察、流程观察、Bot 挑战、统一决策和配置发布基础。下一阶段应从“增加检测项”转向三个可验收目标：

1. **检查是否完整可证明**：展示真实执行范围、跳过原因、节点覆盖和证据缺口，而不是仅统计规则数量。
2. **高置信违规可控阻断**：对象授权、业务流程、协议资源滥用在满足信任条件时进入 PROTECT；未知、推测和依赖故障另行处理。
3. **新协议与智能体可治理**：补齐 GraphQL、gRPC、MCP 的协议语义、资源预算和调用权限，不依赖关键词扫描冒充完整防护。

建议按以下优先级推进；每次只启动一个明确阶段或模块，不同时铺开七条开发线。

| 优先级 | 研发方向 | 主要收益 | 首期边界 |
|---|---|---|---|
| P0 | 防护覆盖度与安全验证闭环 | 让现有和新增能力可验证、可灰度、可回退 | 执行覆盖账本、证据对账、离线模拟 |
| P0 | HTTP 解析链一致性 | 降低代理与源站解释差异导致的绕过风险 | 隔离回归与配置约束，不重写 HTTP 栈 |
| P1 | GraphQL 语义与资源预算 | 防止浅层但高代价查询、别名与批处理滥用 | HTTP query/mutation；订阅另立范围 |
| P1 | BOLA/BFLA 高置信授权防护 | 从发现越权线索升级为选择性阻断 | 可信主体、明确角色、单一 OWNER 对象 |
| P1 | 业务流程强约束 | 防止跳步、乱序、并发重复执行 | 经确认的流程及业务成功判定 |
| P1 | gRPC 深度检测 | 补齐压缩、一元调用、字段结构检测 | unary 优先；流式调用分阶段 |
| P2 | MCP 工具调用防护 | 约束智能体工具权限、参数和结果 | 可被 WDSP 代理的远程 HTTP MCP |
| P2 | 机器客户端可信身份 | 区分可验证机器身份与弱指纹 | DPoP 或签名客户端二选一试点 |

这里是七个功能方向加一项 HTTP 工程专项。若近期客户明确部署 MCP，可在阶段 0 调整其顺序；不得因此跳过共用安全门禁。

### 1.1 成功的定义

- 对开启 PROTECT 的精确范围，能够证明“身份可信、输入受检、策略匹配、最终处置执行、源站是否收到请求”。
- 对未检查或不能检查的流量，给出 `PARTIAL/SKIPPED/ERROR` 等真实状态，不显示为安全通过。
- 所有新增能力默认关闭；现有 OBSERVE 策略不因升级变为阻断。
- 管理面、网关、审计、权限、数据库迁移、接口文档、回归语料和离线交付共同完成，才算模块完成。
- 真实环境验收单独登记为待部署后执行；不能用 Mac 冒烟结果代替 openEuler/兆芯实测。

### 1.2 不在本轮范围

- 不替代业务系统的最终授权、事务一致性或数据库约束。
- 不把“首次访问者”“历史最常访问者”自动认定为对象所有者。
- 不承诺仅凭代理实现跨业务服务的 exactly-once 执行。
- 不对每个请求调用外部大模型，不把模型判断直接作为阻断依据。
- 不开发通用 IAM、完整 SOAR、通用工作流引擎或任意代码策略执行器。
- 不开展未授权真实系统扫描，不向生产源站回放请求，不自动修改系统 Docker 或防火墙。
- 不复制其他产品的代码、接口、表结构或界面；仅参考公开技术原理。

以下为技术方向依据；后文的字段、阈值、任务和排期是本项目的设计提案，并非引用来源的产品承诺。协议版本、依赖版本与许可证须在阶段 0 再核实、锁定。

| 一手资料 | 时间或成熟度 | 对 WDSP 的启示 |
|---|---|---|
| [GraphQL 官方安全指南](https://graphql.org/learn/security/) | 官方持续维护指南；2026-10-03 查阅 | 需求控制需要考虑深度、宽度、批处理、复杂度和可信操作文档，不能只依赖普通请求频率 |

| [PortSwigger CRLF-powered desync 研究](https://portswigger.net/research/crlf-powered-desync-attacks) | 2026-08-05 研究文章 | 请求改写与多跳解析也是风险面；应验证实际代理链，而非只验证单个解析器 |
| [MCP Security Best Practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) | 本文引用固定 `2025-11-25` 文档路径，不宣称它是最新协议 | 明确 Token 受众、禁止 Token passthrough，防止混淆代理与授权元数据访问风险 |
| [OWASP Agent Control Standard 资源页](https://genai.owasp.org/resource/agent-control-standard-acs/) | 2026-09-01 发布的项目资源 | 智能体执行过程需要可检查、可追踪的控制点；不是 WDSP 已满足的认证标准 |
| [RFC 9449：DPoP](https://datatracker.ietf.org/doc/html/rfc9449) | 已发布 RFC | Token 与客户端持有的密钥绑定，需要授权服务器和客户端配合 |
| [RFC 9421：HTTP Message Signatures](https://datatracker.ietf.org/doc/html/rfc9421) | 已发布 RFC | 可验证签名覆盖的 HTTP 消息成分；仍需自行明确身份登记、重放防护与权限 |
| [Cloudflare Signed Agents](https://blog.cloudflare.com/signed-agents/) | 2025-08-28 产品与技术介绍；相关代理身份生态仍在演进 | 机器身份可验证不等于自动可信，更不等于跳过 WAF/API 策略 |

研究报告揭示的是风险类别，不是“WDSP 已存在相应漏洞”的证据。HTTP、MCP 等专项必须以本项目隔离复现结果决定是否需要产品修复。

### 3.2 实现与历史文档存在差异时的处理

- 当前统一决策实际优先级为 `BLOCK > TEMP_BLOCK > RATE_LIMIT > MASK_RESPONSE > OBSERVE > ALLOW`；本方案不按旧文档的不同排序开发。
- 当前决策引擎允许部分高分 Finding 触发阻断。新增“覆盖不完整”“依赖不可用”等信号不能只写 `OBSERVE` 再赋高分，否则可能意外变成 BLOCK。
- 对象授权已有撤销、重新授权及同步相关实现。本轮要验证传播和回退边界，不能把“缺乏完整生产验收”描述成“没有同步功能”。
- 流程观察已有分布式状态接线，但不等于已具备面向阻断的业务事务状态机。
- 测试文件存在不等于本次已通过测试；本次未运行产品测试。
- [VERSION.md](../VERSION.md) 在调研时登记已发布 `1.2.0`、候选 `1.2.1`。现场包名或历史对话不是仓库发布事实；实施时须核对实际运行版本，本文不预定下一版本号。

## 4. 总体架构与共用安全契约

### 4.1 复用现有架构

```text
管理面：现有策略 / 授权关系 / 流程基线 / 协议资产
                 │ 草稿校验、权限与审计
                 ▼
现有编译与发布链：不可变快照 + 内容摘要 + 能力需求 + 节点确认
                 │
                 ▼
网关既有请求链 → API 管线内的协议解析 / 语义检测 → 统一决策 → 协议适配执行
                          │                           │
                          └── 受检范围与原因 ─────────┴── 执行结果
                                                  │
                                                  ▼
                                  现有事件 / 授权审计 / 覆盖汇总

响应返回 → 有界响应检查 / 流程成功确认 → 独立记录已转发与已处置事实
```

此图只展示本轮扩展位置，不替代 [AGENTS.md](../AGENTS.md) 中完整处理顺序。不得移动真实 IP、JWT、白名单、CC、Bot、WAF 等现有步骤；跨中间件改动必须通过真实 Caddy 集成测试。

### 4.2 必须维持的安全不变量

1. 白名单、保护地址或 L7 allow 不绕过 WAF、API 动态防护、Bot 和 JWT PROTECT 的既有底线。
2. 主体、租户和角色必须来自验证后的身份链；请求体、普通头或模型生成文本中的声明不可信。
3. 本轮新增检测器只提交证据与候选动作；不得自行写 HTTP 响应绕过统一决策。响应阶段按既有阶段契约收敛，不能重新执行已经转发的请求。
4. 区分“已确认违规”“未知”“基础设施故障”“不支持的协议”；只有第一类自然进入违规阻断。
5. 规则例外须有范围、有效期、操作者和理由；不删除原始命中证据，不把单条例外扩展为整条管线绕过。
6. 请求热路径不新增公网访问。权威关系、Schema、描述符、公钥和工具目录通过控制面显式导入、验证、发布。
7. 内部 Valkey 访问也必须有超时、并发上限和明确故障策略；“无公网请求”不等于“无依赖风险”。
8. 日志不记录原始 Token、Cookie、私钥、完整对象标识、提示词或工具结果；低熵敏感值不能只做普通 SHA-256 后称为匿名。
9. 新能力缺配置默认 OFF；现有能力默认值保持原样；解析器硬资源上限与业务处置模式分别定义。
10. 签名、哈希和离线打包不替代权限审查、运行验证和可恢复性测试。

### 4.3 模式与发布状态分离

运行模式沿用 OFF、OBSERVE、PROTECT。拟在现有发布记录上增加生命周期信息，而不是再造一套策略系统：`DRAFT → VALIDATED → SHADOW → CANARY → ACTIVE`，失败进入拒绝发布或回退流程。

- `OFF`：不执行该新增业务检测；仍执行必要的协议解析安全限额及既有独立防护。
- `OBSERVE`：可以记录“若启用将阻断”，不执行该新增模块的阻断、限速或响应改写。
- `PROTECT`：只有全局 API 模式、功能模式、范围选择、节点能力及证据资格全部满足时，才允许实际动作。
- 全局 API 为 OFF/OBSERVE 时，不能通过子策略启用 PROTECT；此前独立执行的 WAF、JWT、CC、Bot 语义不因此关闭。
- SHADOW/CANARY 是发布过程，不是绕过全局模式的后门。流程灰度必须对整个流程实例稳定分组，不能每个请求随机切换。

### 4.4 拟新增的公共逻辑契约

下列是设计字段，不是仓库已经存在的 Go 类型或数据库列。阶段 0 必须评审字段名、版本、兼容策略并更新 OpenAPI/配置契约。

| 逻辑对象 | 必要信息 | 约束 |
|---|---|---|
| `CapabilityManifest` | 节点版本、协议版本、解析器/检测器能力、支持动作、资源限额 | 能力缺失不能 ACK 成功；不能仅比较产品版本字符串 |
| `CoverageObservation` | 请求关联、检测器、阶段、目标范围、状态、原因、检查字节/消息数、截断、策略版本 | 独立于攻击 Finding；不得贡献攻击分数 |
| `EnforcementEvidence` | 可信主体来源、证据来源、快照版本/有效期、规则版本、确定性判定、阻断资格 | 新能力只以显式资格进入动作；保留旧检测器行为兼容测试 |
| `ExecutionOutcome` | 候选动作、最终动作、实际执行、协议状态、是否已转发、失败原因 | “计划阻断”和“已阻断”必须分开 |
| `SnapshotWatermark` | 关系版本、撤销水位、签发/失效时间、节点应用时间 | 安全水位不可被普通策略回滚降低 |

新增明确阻断资格时，采用版本化增量接入，先适配新模块；不得一次重写所有旧检测器的评分和动作规则。未迁移旧模块要保留黄金样本，证明结果不变。

### 4.5 故障与未知处理矩阵

| 情况 | 默认处置 | 可选严格策略 | 必须展示的事实 |
|---|---|---|---|
| 授权对象未匹配、缺可信主体 | UNKNOWN，继续既有防护；鉴权要求仍由 JWT 等执行 | 特定端点可拒绝“不满足准入条件”，不能伪称已证实越权 | 缺什么证据、适用范围 |
| 关系快照过期/验签失败 | 不使用该快照得出可信授权；记录降级 | 预先批准的受保护端点按依赖不可用返回 503 或协议等价错误 | 快照版本、过期/验签原因 |
| 权威关系同步中断 | 仅在有效租约内使用已验证快照 | 租约到期后严格拒绝，或按明确策略降级观察 | 数据年龄、租约、未确认节点 |
| Valkey 不可用 | 观察型路径可按原设计降级；不声称跨节点一致 | 强流程/重放防护不得偷偷降级本地内存；按批准策略拒绝或暂停该保护 | 一致性不可用，不是攻击确认 |
| 报文/解压/AST 超过硬上限 | 停止解析，保护网关资源 | 已配置的准入资源上限可拒绝；响应码按协议冻结 | LIMIT_EXCEEDED，不是解析成功 |
| 流式响应已向客户端输出 | 停止后续违规输出的能力单独声明 | 必须全量结果检查的接口应在发布时拒绝不兼容配置 | 已转发字节不可撤回 |
| 节点不支持新契约 | 拒绝该节点应用新策略 | 不允许“忽略未知字段后继续 PROTECT” | 节点能力缺口、发布失败 |
| 观测/证据队列满 | 按有界队列策略丢弃低优先级明细，保留丢弃计数 | 关键变更审计持久化失败则拒绝该管理操作 | 不显示完整证据 |

服务端内部故障不能映射成“无效 Token”的 401；资源依赖故障不能伪装成越权 403。严格策略会影响可用性，必须按业务端点单独批准。

## 5. 方向一：覆盖度、验证与灰度闭环

### 5.1 覆盖度不能用规则数量替代

沿用现有授权覆盖、准入覆盖和运行态事件，补一层跨检测器执行覆盖。按“应用、端点模板、协议、方向、检测器、策略版本、节点、时间窗口”聚合，维度组合设上限。

拟定状态：

- `FULL`：在该记录明确声明的范围内全部完成；仅检查首帧时，范围只能写首帧，不能写整条 gRPC 流。
- `PARTIAL`：执行过但存在截断、抽样、未覆盖字段/消息或只看到一侧。
- `SKIPPED`：本应可评估但因关闭、规则选择、能力缺失或依赖条件未满足而未执行，附原因。
- `ERROR`：执行异常或结果不能使用；不转成 FULL。
- `NOT_APPLICABLE`：按已冻结的分类规则确定不适用；不能用来隐藏超限和错误。

请求未进入某一后置检测器时，区分“上游已拒绝”“API 管线未启用”和“统计缺失”。仅在 API 管线内打点无法覆盖前两者，需在现有请求入口/出口做最小计数接线，不改变处理顺序。

### 5.2 指标口径

- 定义某检测器在窗口内应评估集合 `E`；`E = FULL + PARTIAL + SKIPPED + ERROR`，确定不适用另计。
- 完整检查率为 `FULL/E`；有效执行率为 `(FULL+PARTIAL)/E`，两者不可混用。
- `E=0` 显示“无适用流量”，不显示 100%；统计输入本身不完整时显示“数据不完整”。
- 命中率、实际阻断率和业务误报率分别统计；未知真值流量不能计算漏报率。
- 汇总计数尽量全量；详细证据可以采样，但必须记录采样率、丢弃量和对账差异。
- 授权覆盖应额外显示：可信主体覆盖、已确认对象关系覆盖、有效快照覆盖、UNKNOWN 原因分布。
- 避免用户 ID、对象 ID、原始 URL、Token 指纹成为指标标签；仅在权限隔离的明细中使用受控关联值。

### 5.3 安全验证机制

提供两种明确区分的验证方式：

1. **无副作用模拟**：冻结策略和脱敏证据，在隔离的解析/决策实例内运行，不反向代理、不调用工具、不修改真实流程/限速/重放状态。缺原始输入时标记不能复现，不能补造输入证明通过。
2. **隔离集成回放**：使用已授权合成语料，连到测试源站；所有出站目标均在允许清单，逐跳重定向复检，不对生产系统进行“只读 GET 回放”。GET 也可能有副作用。

模拟结果包括：旧/新策略差异、拟新增阻断、证据不足、协议不可复现、例外命中、资源成本。模拟不是 PROTECT 实测，不能单独满足上线条件。

### 5.4 管理界面与验收

- 复用 API 运行时策略、事件、授权页面；新增“覆盖与验证”视图，不另建同名策略入口。
- 每条建议提供证据、支持/不支持的范围、影响端点和预计动作；启用前有明确确认。
- 发布前检查节点能力、模拟报告时效、策略摘要一致性；策略或输入变更后旧报告失效。
- 灰度按应用/端点/可信主体稳定分桶；缺可信主体时使用明确接入分组，不用容易变化的指纹猜身份。
- 支持停止灰度和回退策略；撤销关系水位、重放记录和业务执行事实不能随策略回退复活。
- 验收必须构造 FULL/PARTIAL/SKIPPED/ERROR/缺节点五类数据，检查页面、API、导出和统计一致。

## 6. 工程专项：HTTP 解析链一致性

目标是验证“客户实际接入链中的每一跳如何解释请求”，不是在业务检测器中写一个新的 HTTP 解析器。

### 6.1 链路清单

登记测试拓扑：直连 WDSP、前置可信代理、HTTP/2 到 HTTP/1.1 转换、HTTP/3（实际启用时）、路径重写、源站转发，以及不同源站协议实现。记录 Caddy、Go、Coraza、适配器和源站的锁定版本。

覆盖项：重复/冲突长度头、传输编码歧义、非法换行、URL 解码与重写、Host/authority 不一致、绝对形式请求、重复敏感头、HTTP/2 伪头、请求体边界、连接复用后继请求、升级协议边界。具体危险样本仅放隔离测试语料，不写入生产运行包。

### 6.2 实施方式

- 在专用测试源站记录规范化后的方法、路径、头结构、请求计数和体摘要，不记录真实凭据。
- 对比网关安全判断与源站实际收到的边界；不能只看客户端状态码。
- 无法在业务层可靠观察的畸形报文，由底层服务器拒绝并以连接行为/源站计数验收。
- 若发现版本缺陷，优先评估上游修复和受支持配置；依赖升级必须重新锁版本、镜像摘要并做回归。
- 不做未经证明的多次 URL 解码或请求重写；不得通过“规范化”制造新的解释差异。
- 确认真实 IP 和外部 URL 只消费可信代理来源，防止影响 JWT/DPoP 与授权范围匹配。

完成标准：每个声明支持的链路有独立正常/异常用例及连接复用验证；无测试拓扑的组合标注未验证，不宣称普遍免疫请求走私。

## 7. 方向二：GraphQL 语义与资源预算

### 7.1 功能设计

- 通过端点配置与 Content-Type 识别 GraphQL，保留兼容识别逻辑；不只依赖路径包含 `/graphql`。
- 引入有界 AST 解析与 Schema 校验。解析库先评估许可证、维护状态、恶意输入耗时与依赖体积，再锁版本。
- 精确选择 `operationName`；多操作未选择、操作不存在、语法错误和合法多操作文档要分别处理。
- Fragment 展开必须有循环检测、最大展开节点数及工作预算；alias 以真实执行字段计费，不能去重后少算。
- 变量、默认值、列表参数和指令纳入成本计算；不能求值的分支采用明确保守上界或标为未知。
- 区分文档内多个 operation 与 HTTP JSON 数组批处理；只执行被选 operation，不把整份文档所有 operation 都当作一次执行。
- Schema、字段权重、最大列表规模、批处理开关和可信操作文档分别版本化，随现有策略发布。

### 7.2 成本与资源控制

拟采用可解释的递归预算模型：`cost(selection) = Σ[字段基础成本 + 返回规模上界 × cost(子选择集)]`；叶子字段的子选择集成本为 0，但字段基础成本仍计费。非列表字段的规模系数为 1，列表字段使用经批准的上界；按元素计算的业务成本计入相应权重。实际算法、重复字段合并规则、默认列表上界在阶段 0 冻结，并用真实执行样本校准。

- 单请求预算与主体/租户时间窗预算分开；匿名请求有单独策略，不默认共享一个全站桶。
- 所有乘加使用溢出检查和饱和上限，成本溢出视为超限，不变成小数值。
- AST 节点、深度、alias、batch、变量体积、解析耗时、并发解析数和缓存内存均有上限。
- 缓存键包含文档摘要、Schema 版本和策略版本；变量相关成本不得错误复用固定结果。
- APQ/持久化查询不自动等于可信文档；只有经过审核登记的摘要才能进入可信白名单。
- OBSERVE 记录拟处置；PROTECT 在请求进入源站前执行。结构准入失败和时间窗限额失败分开映射响应。

### 7.3 边界与验收

首期仅承诺 HTTP query/mutation。订阅、WebSocket、multipart 增量结果和联邦内部调用须另行登记；没有实现时在覆盖页显示不支持或部分覆盖。

资源控制不能代替字段级业务授权。测试需证明：正常深查询可按批准预算通过；浅而昂贵查询被识别；合法 fragment/变量不误判；恶意递归和超大 batch 在有界时间内结束；超限请求未到达源站。

## 8. 方向三：对象与功能授权的高置信 PROTECT

### 8.1 复用与扩展

保留现有候选、人工确认、撤销、重新授权、覆盖和决策接口。新增的是“什么证据允许实断”及证据更新保证，不是重新实现关系 CRUD。

首批支持：

- 经 JWT 信任链验证的主体、租户和角色；角色映射由管理员配置并版本化。
- 唯一端点模板、单一对象定位、明确 OWNER 排他语义。
- 关系来自人工核实或经验证的业务权威同步；历史访问推断只能成为待确认候选。
- BFLA 仅对明确角色到动作的批准矩阵执行，不把从历史请求学到的角色基线直接转换为拒绝策略。

暂不宣称支持：共享对象、委托、复杂组继承、嵌套租户、批量对象、复合 ID、对象字段级授权。后续扩展必须单独建模、测试和发布。

### 8.2 权威关系输入

优先建设离线签名导入和业务系统主动推送两种入口；自动拉取仅在用户明确配置授权后建设，不在请求热路径访问业务系统。

拟定输入包含：来源 ID、事件 ID、单调序列、对象类型、租户域、主体引用、关系、有效期、签发时间、来源签名和变更类型。接入必须验证来源身份、重放、范围权限、大小和字段白名单。

- 全量快照采用暂存、完整性校验、原子切换；导入中断不能把未导入对象全部当作撤销。
- 增量必须检测序列缺口、重复和乱序；缺口未补齐时标记数据不完整，不伪造最新状态。
- 同一对象出现冲突所有者时进入冲突状态，不能按“最后到达者”覆盖成可信关系。
- 对象引用采用已有 HMAC 域隔离机制；密钥轮换期间的双版本匹配和清退必须明确。
- 来源密钥、发布签名密钥、对象 HMAC 密钥不能混用；私钥不下发至流量网关或升级包。

### 8.3 决策与撤销传播

拟定决策语义：`ALLOW / VERIFIED_VIOLATION / UNKNOWN / DEPENDENCY_UNAVAILABLE`。与现有 `OBSERVE_VIOLATION` 的兼容映射在契约评审中确定，不能直接修改历史 API 枚举而不迁移消费者。

只有主体可信、模型适用、关系有效且无冲突、范围一致、证据满足要求，才能认定 VERIFIED_VIOLATION。有效 OWNER 是别人不代表所有共享业务都越权，因此模型必须显式声明排他所有权。

撤销处理：

1. 管理面已有撤销接口产生新变更版本；新增持久化撤销水位并通过现有发布链传播。
2. 网关收到并验证水位后，不得回退到水位以前的授权快照。
3. `PreviousValid` 仅能回退到仍有效且不越过撤销水位的快照。
4. 回滚策略不回滚撤销事实；恢复授权必须经过现有重新授权流程并产生新审计记录。
5. 断连节点在租约有效期内仍可能持有旧状态，不能承诺即时全局撤销；必须显示未 ACK 节点及最大陈旧窗口。
6. 需要更强保证的端点可在租约过期后停止授权性放行；源站仍保留最终授权校验。

首期候选验收目标：正常测试网络下撤销 ACK 的 P99 不超过 5 秒，关系租约最长 60 秒；这两个数值是待压测和业务确认的规划目标，不是当前能力承诺，也不代表网络分区时 5 秒全局生效。

### 8.4 前后台与验收

- 授权页面展示来源、有效期、冲突、最后同步时间、节点 ACK 和当前能否实断。
- 关系管理、策略发布和证据明细继续分权；只有读取权限的人不能确认关系或启用 PROTECT。
- 切换 PROTECT 前必须选定端点、业务负责人、证据来源和 UNKNOWN 处理方式；默认保持 OBSERVE。
- 集成测试同时断言客户端响应、源站是否收到请求、授权决策记录和运行态事件。
- 必须通过跨租户同名对象、撤销后回滚、快照过期、旧节点、断网、时钟偏差和重新授权用例。

## 9. 方向四：响应确认型业务流程防护

### 9.1 为什么不能直接将现有流程观察改为阻断

现有流程检测可依据观察到的请求推进状态，适合发现线索。但“发出了支付请求”不等于“支付成功”；超时也不代表业务回滚。因此实断状态必须与观察状态分离，使用新的版本化状态命名空间，旧状态不能直接导入作为可信已完成步骤。

### 9.2 状态与原子操作

拟定流程实例键：应用 + 可信租户 + 可信主体 + 流程定义版本 + 实例引用。实例引用来自批准的字段提取器，做域隔离 HMAC；不是单纯按客户端 IP 分组。

```text
CONFIRMED(state=A)
  └─ reserve(operation_id, expected_version) → PENDING(A→B, lease)
       ├─ 明确业务成功 → commit → CONFIRMED(state=B)
       ├─ 明确业务未执行/失败 → release → CONFIRMED(state=A)
       └─ 超时/断连/结果不确定 → INDETERMINATE → 权威对账或人工恢复
```

- Valkey 使用原子 CAS/脚本完成检查与预留；集群场景相关键必须处于同一原子操作域。
- `operation_id` 和幂等键绑定实例、动作、主体及参数摘要；相同幂等键不同参数必须冲突。
- 预留要有 fencing token，过期旧执行者不得提交新状态；仅靠 TTL 不足以防止迟到响应覆盖。
- 网关关闭或连接取消只标记未知结果，不自动认定失败并允许再次扣款。
- 状态恢复不能伪造业务成功；需要业务回调/查询接口时属于显式接入依赖，默认不联网轮询。
- 网关原子状态不等于源站事务原子性；重复业务执行仍需源站幂等键或数据库唯一约束。

### 9.3 成功判定与流程语义

- 由管理员为每一步配置“请求范围 + 成功响应条件 + 可重试语义”，经业务负责人确认。
- HTTP 2xx 不是通用成功证据；GraphQL 要考虑 `errors`，gRPC 要考虑 trailers 中的业务/协议状态。
- 可选成功证据包括受信任源站连接上的状态与受限字段，或业务签名回执；明文不可信链路不作为高置信来源。
- 回调和长任务采用“已受理/待完成/已完成”分态，不把 202 自动记为完成。
- 明确取消、补偿、重启流程、重复读取、并行合法步骤和部分成功；不建立“取消后永久不能重新开始”的全局粘滞状态。
- 先支持可完整观察的一元交互；流式、超大响应、跨系统补偿列为不支持或需要业务回执。

### 9.4 发布、管理与验收

流程定义更新后，新实例使用新版本；存量实例固定旧版本完成或按审核方案迁移，不能中途换图。严格流程在分布式状态不可用时不得静默切换本地内存。

复用流程基线页面，增加状态图、允许转换、成功条件、异常策略、实例恢复记录。每次管理恢复需理由、权限和审计；不能提供无审计的“一键置成功”。

必须验证双节点并发、同幂等键重试、不同参数重试、延迟成功响应、节点重启、Valkey 故障、业务超时但实际成功、取消后新实例以及策略回滚。结果未知时显示 INDETERMINATE，不能显示流程安全通过。

## 10. 方向五：gRPC 有界深度检测

### 10.1 分期范围

| 子阶段 | 交付范围 | 不得扩大宣称的边界 |
|---|---|---|
| G1 | unary 请求/响应、批准的压缩算法、描述符校验、repeated/map/oneof | 不代表支持所有 codec、gRPC-web 或任意流 |
| G2 | server streaming 的逐消息检查与背压 | 已放行消息不能撤回；不是全流事务 |
| G3 | client/bidi streaming 的逐消息策略及会话预算 | 依赖客户端取消/重试兼容验证，不纳入首期完成条件 |

当前 `MaxGRPCFrameBytes` 默认 4 MiB，而公共完整 Body 解析上限默认 1 MiB。两者是不同层级的限制，不等于当前能完整深检 4 MiB 消息；G1 必须解决协议专属读取预算与公共解析预算的衔接。

### 10.2 技术设计

- 描述符离线导入、校验依赖闭包、限制总大小/类型数，按 service/method 和内容摘要版本化；不在热路径访问 Reflection 服务。
- 从帧头分阶段读取，先验证声明长度再分配内存；消息边界跨 TCP/HTTP 数据片段也应正确处理。
- 压缩标志与 `grpc-encoding` 联合判断，先支持批准算法；压缩字节数、解压字节数、倍率及 CPU 工作预算分别设限。协议依据见 [gRPC 压缩指南](https://grpc.io/docs/guides/compression/)。
- 描述符检查覆盖标量、嵌套、repeated、map、oneof、未知字段和枚举；字段存在性按 protobuf 语义处理，不把默认值误当缺失。
- 不因检查而重新序列化正常请求，以免改变未知字段、签名或业务字节语义；需要响应改写时必须另行批准并正确重算相关元信息。
- 对单消息、单 RPC、单连接及网关总缓冲分别限额；流式采用有界消息缓冲与背压，禁止无限缓存完整流。
- 取消和 deadline 到达后释放缓冲与解析任务，用泄漏测试证明不会持续占用 goroutine。若已转发有副作用请求，强流程预留按第 9 节转为 INDETERMINATE；不得因释放传输资源就清除执行事实或自动允许重试。

### 10.3 执行与验收

统一决策应调用协议适配执行层，而不是向 gRPC 客户端返回 HTML 或普通 HTTP 403 页面。拟按认证、权限、资源和依赖失败分别映射 `UNAUTHENTICATED`、`PERMISSION_DENIED`、`RESOURCE_EXHAUSTED`、`UNAVAILABLE`，精确 trailers/响应行为在 G1 契约中冻结并与真实 SDK 对测。语义依据见 [gRPC 状态码](https://grpc.io/docs/guides/status-codes/)。

覆盖记录至少包含消息方向、消息序号、压缩方式、描述符版本、实际读取/解压量和已转发消息数。首条正常、第二条违规的流式用例不能错误报告“整个调用通过”。

G1 必测：分片帧、空消息、错误长度、未知编码、解压膨胀、重复字段、大 map、oneof、超时取消、未知描述符和真实客户端错误处理。G2/G3 未实施时，页面及交付说明明确为部分覆盖。

## 11. 方向六：MCP 工具调用安全

### 11.1 能力定位与协议范围

建设“可验证的工具调用控制”，而不是把敏感词检测改名为 AI 防火墙。首期处理经 WDSP 代理的远程 HTTP MCP；协议协商、传输方式、JSON-RPC 消息和会话生命周期按阶段 0 冻结版本实现。

- 本地 stdio 调用不经过反向代理，必须依赖客户端/SDK 拦截器或专用桥接，首期不覆盖。
- SSE/流式传输要明确每条逻辑消息的检查边界与断连恢复；不是把 HTTP 响应前缀作为完整工具结果。
- 合法扩展方法默认记为未知能力或按策略处置，不能仅因不在硬编码列表就判为攻击。
- MCP 认证与工具授权分别检查；调用方 Token 受众必须匹配目标服务，不将上游 Token 任意转交下游。

### 11.2 工具目录与确定性策略

工具目录拟包含：服务身份、工具名、工具描述摘要、输入/输出 Schema、版本、能力标签、风险级别、数据分类、允许主体/角色/租户及审批要求。

1. 管理面显式导入或通过获批连接器同步目录；新工具和目录变更先进入待审核。
2. 策略绑定工具版本/摘要；工具同名换描述或 Schema 后不能继承旧审批自动获得权限。
3. `tools/call` 在转发前检查可信主体、工具白名单、参数 Schema、路径/域名/动作范围和调用预算。
4. 参数校验覆盖对象深度、数组长度、字符串长度、未知字段和重复 JSON 键策略；不能只检查截断后的 256 字符。
5. 输入中“我是管理员”“忽略限制”等内容只作为风险线索，不能改变调用方权限。
6. 工具结果按批准的数据规则检查；敏感数据字段确定性规则优先，模型判断只能辅助人工分析。

调用、结果和执行侧出网是三个不同控制面。入站 WDSP 无法自动阻止工具进程访问任意内网地址；需要 SSRF 出网约束时，应另行接入受控出口或工具沙箱，不承诺单靠反向代理解决。

### 11.3 高风险操作审批

首期可对高风险工具默认拒绝并返回可关联的安全事件；这不等于已实现审批闭环。

完整审批作为有业务客户端配合的子阶段：申请绑定主体、租户、工具摘要、规范化参数的受密钥保护摘要、有效期及单次消费标记；审核后客户端重发，网关验证并原子消费许可。参数、工具版本、主体或范围变化必须重新审批。

- 不能无限挂起原请求等待人工审批；超时、取消、重复申请和许可泄漏有明确行为。
- 审批请求与实际业务执行不是同一事务；仍需工具端幂等配合，避免消费许可后断网造成盲目重试。
- 禁止通过只读管理员权限批准有副作用操作；审批与策略发布是否要求双人复核在阶段 0 决定。
- JSON-RPC/MCP 错误响应按冻结协议定义；自定义错误要明确为产品扩展，不能冒用标准错误语义。

### 11.4 隐私与验证

默认仅留字段路径、命中类型、内容长度、受控摘要和关联号，不存原始提示词、访问 Token 或工具返回全文。排障采样必须显式开启、限时、脱敏、限制访问并审计。

测试至少包括：未授权工具、同名工具变更、伪造角色、参数嵌套绕过、结果泄漏、长流、未知扩展、审批重放及跨租户复用。验证“未授权调用确实没有到达测试工具”，不能只验证管理面产生告警。

## 12. 方向七：可选机器客户端可信身份

### 12.1 两条路线，不同时强推

| 路线 | 适合场景 | 外部依赖 | WDSP 职责 |
|---|---|---|---|
| DPoP | 可改造 OAuth 授权服务器和客户端的 API | 发行绑定公钥的 Token、客户端生成请求证明 | 验证 Token 绑定、证明、目标方法/URI、有效期及重放 |
| HTTP Message Signatures | 可登记机器身份和公钥的受控集成/Agent | 客户端按约定签名，服务端管理身份和权限 | 验证约定签名成分、有效期、nonce、撤销及权限 |

先选一个实际客户场景完成端到端试点。不要把任意 Bearer Token 包装成 DPoP，也不把某个厂商的试验性 Agent 标识协议当成通用强制标准。

### 12.2 接入要求

- 公钥管理使用静态离线导入或控制面批准的同步；禁止根据请求中的任意密钥 URL 自动抓取。
- DPoP 具体校验遵循 RFC 9449；需检查请求绑定、Token 哈希、证明 ID/时间、密钥绑定和必要 nonce。证明存在不等于已通过客户端授权。
- 签名身份明确覆盖成分，涉及 Body 时必须验证其内容摘要；未签名的权限关键头不得进入可信上下文。
- 反向代理后的外部 URI 规范化必须按所选协议处理，DPoP 与 HTTP 签名规则不能混用；只信任批准的转发信息。
- 多节点重放记录使用原子共享存储；状态不可用时按明示严格策略处理，不悄悄只在本机去重。
- 密钥轮换有重叠窗口和撤销水位；旧节点与旧密钥状态要显示，不能让普通策略回滚恢复已撤销密钥。
- 验证成功的机器身份仍经过授权、资源预算、WAF 和 API 防护；是否免浏览器挑战必须是精确范围的显式策略。

### 12.3 不纳入首期的弱指纹扩展

现有 TLS 版本/密码套件组合只能作为弱特征。JA3/JA4、设备指纹、行为相似度等可独立调研，但须核查采集位置、隐私、许可证和误报，不作为确定性身份或对象所有权证据。

## 13. 数据模型、接口与管理面契约

### 13.1 数据模型策略

优先扩展现有模型与事件，不先建一个包揽所有模块的通用规则数据库。以下是逻辑实体提案，物理表名、索引、迁移编号在阶段 0 检索现有 schema 后确定，不预占迁移序号。

| 逻辑实体 | 复用/新增方式 | 关键字段与一致性 |
|---|---|---|
| 策略能力扩展 | 扩展现有 API 策略 | 功能开关、范围、预算、未知策略、Schema 版本、乐观锁 |
| 协议资产版本 | 复用已有导入/编译机制，按协议扩展 | GraphQL Schema、gRPC 描述符、MCP 工具目录；不可变摘要 |
| 授权权威来源 | 拟新增元数据及导入批次 | 来源范围、公钥引用、序列水位、完整性、更新时间、状态 |
| 授权关系与撤销 | 扩展现有关系/快照 | 来源证据、撤销水位、有效期；禁止删除审计以“回滚” |
| 强流程实例 | 独立于现有观察状态的版本化命名空间 | 状态、CAS 版本、预留、fencing token、租约、未知结果 |
| 覆盖聚合 | 拟新增或扩展现有统计存储，按容量评估 | 有界维度、窗口、五态计数、丢弃/缺节点、数据版本 |
| 验证运行 | 对接现有回归证据和发布门禁 | 策略摘要、语料摘要、节点能力、工具版本、状态、过期时间 |
| 机器身份登记 | 复用可信密钥管理原则，拟新增业务实体 | 身份、租户、公钥引用、算法、范围、有效期、撤销水位 |
| MCP 审批许可 | 仅完整审批子阶段新增 | 参数绑定、审批人、单次消费、过期、审计，不保存原始凭据 |

关键唯一性：来源事件 ID、来源单调序列、流程操作 ID、验证报告与策略摘要绑定。租户/应用范围必须进入唯一约束与查询条件，不能仅依赖前端过滤。

### 13.2 接口复用与拟新增接口

下面“现有”路径已在仓库中核对；“拟新增”是设计候选，不能据此认为可直接调用。

| 状态 | 接口或资源 | 用途 | 权限处理 |
|---|---|---|---|
| 现有，扩展字段 | `GET/PUT /api/v1/api-security/policy` | 新能力配置与版本化校验 | 沿用 `api_policy.read/edit` |
| 现有，扩展发布门禁 | `POST /api/v1/api-security/policy/publish` | 校验能力、证据与灰度条件 | 沿用 `api_policy.publish` |
| 现有，扩展返回 | `GET /api/v1/api-security/runtime/events` | 展示候选动作、实际执行、受检范围 | 沿用现有读取范围，敏感明细另鉴权 |
| 现有，复用 | `/api/v1/api-security/authz/relations` 及撤销/重新授权子资源 | 管理可信对象关系 | `api_authorization.relation_manage`，不降低现有限制 |
| 现有，扩展 | `GET /api/v1/api-security/authz/coverage` | 展示关系有效性与传播状态 | `api_authorization.read` |
| 现有，扩展定义 | `/api/v1/api-security/flow-baselines` | 强流程草稿、成功判定、版本 | `api_flow.read/manage`；发布权限另按发布链审核 |
| 拟新增 | `GET /api/v1/api-security/protection/coverage` | 统一执行覆盖，不取代授权/准入覆盖 | 候选权限 `api_protection.read` |
| 拟新增 | `POST/GET /api/v1/api-security/protection/validations` 及 `{id}` | 创建无副作用模拟、查询报告 | 候选权限 `api_protection.validate/read` |
| 拟新增 | `/api/v1/api-security/authz/authorities` 及 `imports` 子资源 | 权威来源与离线批次；不混用普通管理员登录凭据做业务推送 | 新增来源管理/导入权限，名称待冻结 |
| 拟新增 | `/api/v1/api-security/mcp/tool-catalogs` | 目录版本、审核状态与能力范围 | 新增目录读取/管理权限，名称待冻结 |

完整审批、机器身份、流程人工恢复等接口在各阶段任务书中冻结；本轮不预先创建占位接口。新增权限要迁移注册、后端校验、前端隐藏/禁用和越权测试全闭环。

通用约束：管理接口鉴权、CSRF、范围校验、分页上限、乐观锁、幂等键、输入限额与审计遵循现有规范。禁止上传路径穿越、任意文件读取、无限压缩解包和任意 URL 拉取。

### 13.3 错误与兼容

- 新增内部 reason code 使用命名空间并固定枚举，例如 `COV_INPUT_TRUNCATED`、`AUTHZ_SNAPSHOT_STALE`、`FLOW_OUTCOME_UNKNOWN`；这些是拟定内部码，不冒充行业标准。
- 候选动作与协议响应分离：HTTP 认证/授权、资源限额、状态冲突和依赖故障分别评审；GraphQL、gRPC、MCP 使用各自协议适配。
- HTTP 大小上限、速率上限和语法错误不能一律返回 403；具体 400/413/429/503 等映射由端点契约确定。
- 新增字段在旧读取端可忽略，不代表旧网关可忽略安全配置；发布必须做 capability negotiation。
- 数据迁移采用 expand → migrate → contract，兼容窗口结束前不删旧字段。回滚应用镜像不自动回滚关系事实或不可逆业务状态。

### 13.4 前端交互

复用 [运行时策略页](../web/src/pages/api-runtime-policies/ApiRuntimePoliciesPage.tsx)、[运行时事件页](../web/src/pages/api-runtime-events/ApiRuntimeEventsPage.tsx)、[授权页](../web/src/pages/api-authz/ApiAuthzPage.tsx) 和 [流程页](../web/src/pages/api-flow-baselines/ApiFlowBaselinesPage.tsx)。实施时遵循九章现有 UI/UX 规范，不在本方案中另定视觉系统。

- 配置顺序：范围 → 可信输入 → 预算/规则 → 失败策略 → 验证 → 发布。
- 页首始终显示当前模式、实际生效版本、节点覆盖与更新时间；草稿不能看起来已生效。
- 明细联动：请求关联号 → 检测证据 → 决策 → 实际执行 → 源站/响应阶段事实。
- 明确区分“未开启”“不支持”“数据不足”“已验证正常”“命中未拦截”和“已拦截”。
- 切换 PROTECT、严格失败策略、恢复流程状态时显示业务影响，并要求理由；高风险操作是否双人复核由权限设计确定。
- 空数据、接口失败、权限不足、长字段和并发编辑冲突分别展示，不以绿色 0 风险掩盖加载失败。

## 14. 容量、隐私与非功能要求

### 14.1 预算必须端到端计算

除单请求限额外，还要限制同时解析数、队列长度、连接消息数、状态键总数和租户占用。网关峰值预算至少包含：并发数 × 请求缓冲 + 响应缓冲 + 解压缓冲 + AST/描述符对象 + 状态与缓存。

超时不能仅用外层 timer 包住不可取消解析器；需要解析工作量计数、可取消循环、受控工作池或有界输入证明。超时后仍持续运行的 goroutine 不算资源保护完成。

初始建议用于隔离实验，非生产默认值：GraphQL 深度 20、展开节点 10,000、alias 100、HTTP batch 10；实际 Schema 与正常业务基线确认后再冻结。预算不足时先标注覆盖不足，不自动提高所有全局上限。

### 14.2 性能候选门槛

以下为阶段 0 讨论用目标，未测量、未承诺达到；必须固定硬件、负载、内容分布和开启模块后比较。普通 amd64 与兆芯分别出报告。

| 模式/场景 | 候选门槛 | 解释 |
|---|---|---|
| 新能力全 OFF | 同负载吞吐降低不超过 2%，P99 增量不超过 1 ms | 对照同源码基线；测量噪声和置信区间必须报告 |
| 覆盖聚合开启、正文检查关闭 | 吞吐降低不超过 3%，队列有界 | 分离计数开销与证据存储开销 |
| 单模块、普通 JSON/GraphQL ≤16 KiB | 固定吞吐下额外 P99 不超过 3 ms，CPU 增量不超过 15% | 仅是预备目标，复杂查询单独分档 |
| 授权本地快照判定 | 无新增网络请求，命中/缺失/冲突均有界 | 不把后台同步时间混入本地判定延迟 |
| 24 小时稳定性 | 无持续内存/状态键增长、无任务泄漏 | 必须在专用环境执行；短时 smoke 不算通过 |
| 故障恢复 | 明确回退状态与恢复时间，不重复业务动作 | 状态恢复正确性优先于追求一个漂亮时延 |

不满足门槛不能通过更换语料、删除异常、关闭必要防护或更改统计分母“修正”。应记录原因，调整实现，或由评审明确更改目标并重跑。

### 14.3 数据保护与保留

- 原始 Token、Cookie、密钥、完整工具结果和提示词默认不落盘；模拟语料优先使用合成数据。
- 受密钥保护的关联摘要属于可关联数据，不是彻底匿名；访问权限和保留期仍需控制。
- 候选保留策略：覆盖分钟聚合 7 天、小时聚合 90 天；事件及授权审计沿用客户已批准策略。数值须由容量和合规评审确定，不自动覆盖当前配置。
- 关键管理变更采用业务记录与审计原子提交或事务 outbox；传递失败可重试且去重。
- 跨节点时钟漂移超过批准上限时禁止启用依赖时效的严格保护，并展示原因；不能靠延长所有 Token/快照有效期掩盖问题。
- 所有新增依赖和镜像锁版本/摘要，优先 Apache-2.0、MIT、BSD；许可证不清晰或 GPL/AGPL 未获书面批准则不得引入。

## 15. 阶段拆分、任务编号与交付物

### 15.1 推荐实施顺序

人周为网关、后端、前端、QA 合计净投入的初步区间，不是单人日历周，也不是交付承诺；阶段 0 后按现有代码复用程度重新估算。业务接入、现场排期和外部标准变动的等待时间不计入。

| 阶段 | 任务编号 | 核心交付 | 前置依赖 | 初估净投入 |
|---|---|---|---|---|
| S0 基线与契约 | NG-BASE-01～04 | 现状复核、接口/状态契约、威胁模型、隔离计划、依赖评估 | 用户确认优先业务 | 2～3 人周 |

## 17. 离线交付、版本与回滚

### 17.1 环境边界

- 安装包继续在 Mac 制作；目标为 openEuler 24.03 LTS-SP4 x86_64，普通 amd64 与兆芯硬件分别验证。
- 测试栈使用独立项目名、随机或明确隔离端口、独立卷；禁止全局 Docker prune、覆盖系统 Docker 或停止其他产品服务。
- 真实环境待用户部署后再验证。本方案不要求当前接入用户真实服务器，更不自动清理现场软件。

### 17.2 包类型与升级通道

- 纯应用能力更新复用现有 `ops/upgrade/build-upgrade-pack.sh` 产出运行时镜像升级包，用户通过前台上传升级。
- 配置/数据库迁移必须随可运行服务和版本清单交付，不以源码差异包充当升级包。
- 若确需基础设施或宿主机组件变更，先论证并明确告知，按完整安装基线流程处理；不能用应用升级通道暗改 Docker、systemd 或防火墙。
- 完整包复用 `ops/offline-package/package-runtime-run.sh`。运行包不含测试代码、研发文档、证据语料和私钥；测试报告单独留在开发交付记录。
- 升级前检查已有新协议基线、节点能力、签名、公钥信任、磁盘空间、数据库备份和回退条件；不满足时在前台明确拒绝。

### 17.3 兼容与回滚矩阵

| 场景 | 允许行为 |

| 旧策略 + 新网关 | 必须保持旧行为；新字段缺省不启用新能力 |
| 新策略 + 旧网关 | 能力门禁拒绝，不可忽略字段后假装生效 |
| 新旧节点混部 | 仅对已验证兼容范围发布；严格防护不能覆盖到未确认节点而不提示 |
| 策略回滚 | 可回退检测配置，不回退撤销水位、已消费许可和已执行流程事实 |
| 应用镜像回滚 | 仅在数据库/状态契约兼容时允许；不兼容则停留安全状态并提供明确恢复步骤 |

### 17.4 版本规则

本次只写方案，不递增产品版本。后续新增能力按功能版本递增第二位，纯 Bug 修复递增第三位，主版本变化需用户明确指示；发布前读取 VERSION.md 并核实分支/tag，不提前承诺某个固定版本号。

只有用户批准发布/推送时，才执行相应版本同步、CHANGELOG、提交、`wdsp-vX.Y.Z` 标签及推送流程。研发完成、构建成功、打包成功、前台升级成功、现场验收通过是五个不同状态，必须分别报告。

## 18. 风险、业务配合与待决策事项

| 风险/依赖 | 影响 | 处理方式 |
|---|---|---|
| 未提交工作区与历史文档不一致 | 容易重复开发或覆盖别人改动 | S0 冻结事实、按模块读取、最小差异；不清理无关修改 |
| 没有可信对象关系或租户声明 | 无法安全做 BOLA 实断 | 先覆盖/观察；等待权威接入，不靠访问历史猜测 |
| 业务成功不可从响应判定 | 流程状态可能误推进 | 业务回执/对账，否则保持观察或未知 |
| 多节点状态与撤销分区 | 陈旧授权、重放或重复流程 | 水位/租约/CAS/fencing；明确可用性取舍 |
| 协议检查带来 CPU/内存放大 | 网关自身可能被耗尽 | 分层预算、fuzz、背压、全局并发限额 |
| MCP 客户端/服务端实现差异 | 错误处理与流式行为不一致 | 冻结兼容矩阵，真实客户端对测 |
| 证据采集泄漏业务数据 | 安全系统成为数据泄漏点 | 默认不留正文，脱敏/限时采样/分权审计 |
| 灰度统计低样本量 | 看似零误报但无统计意义 | 正常业务样本和持续时间同时满足，不只看百分比 |
| 开启严格故障策略 | 依赖故障可能影响业务 | 按端点批准，先影子后灰度，可观察可恢复 |
| 同机其他产品存在 | 安装/测试干扰已部署服务 | 独立资源、只改本产品范围，冲突检查前置 |

阶段 0 需确认的业务问题：

1. 第一批保护哪一类客户接口：普通 REST、GraphQL、gRPC，还是 MCP？默认先覆盖/HTTP/GraphQL，不代表客户一定使用 GraphQL。
2. 哪些系统能提供经确认的主体、租户、角色和对象所有权？谁有权批准关系来源？
3. 哪些业务操作能承受依赖失效时拒绝，哪些必须保持可用并只观察？
4. 能否提供流程成功回执、幂等约束及测试工具？不能提供时不把流程实断列为短期承诺。
5. 是否已有隔离 openEuler/兆芯测试机、两节点测试资源、正常业务合成语料及性能目标？
6. 是否需要 MCP 人工审批、stdio/SDK、受控出口或 gRPC streaming？这些属于单独扩展，不默认包含。

以上待决策不妨碍本文形成；但相关项未确认前，不进入依赖它的实现阶段。
