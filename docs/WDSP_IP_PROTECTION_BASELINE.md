## 4. 信任根与授权事实源

### 4.1 授权信任根

- 正式服务通过 Go `embed` 读取 `server/internal/license/vendor_pubkey.hex`。
- 正式运行时不使用环境变量替换授权公钥集合；`APP_ENV` 也不能重新打开生产测试根路径。
- 测试使用 `wdsp_testkeys` 构建标签或应用装配层显式注入，测试路径必须被构建/发布门禁识别。
- 当前生产公钥文件为空，表示本地仓库尚未具备签发正式授权的生产材料；这不是缺陷修复理由，应该由受控授权发布流程提供并审核后嵌入。

### 4.2 离线包发布信任根

离线包发布签名与授权签名是两个不同的信任域：

- 发布签名用于证明离线包/升级包来源和完整性，相关脚本位于 `ops/lib/signing.sh`，安装侧在执行包内容前验签。
- 授权签名用于证明 `.lic` 的产品、配额、功能、有效期和设备约束，相关实现位于 `server/internal/license/`。
- 两类私钥均不得进入仓库、镜像、离线包、配置或日志；公钥、指纹和版本化信任元数据才允许按审计需要公开。
- 发布公钥的测试/紧急覆盖能力必须与正式发布入口隔离，不能因为安装脚本提供开发逃生开关就把它当作正式门禁通过。

### 4.3 授权原文与数据库

迁移 `server/migrations/000078_license.up.sql` 建立 `licenses` 表。数据库记录包含派生查询字段、签名/载荷以及 `raw_file` 加密留存；生效状态由服务评估，但数据库字段不是独立的授权真值。

正式状态策略必须至少区分：

| 情形 | 允许的结论 |
|---|---|
| 原始 `.lic` 缺失/历史 `raw_file` 为空 | 不可完成数据库篡改复核；不能输出“完整性已验证” |
| 加密服务未装配 | 记录“验证能力不可用/待迁移”，不静默升级为可信 |
| `raw_file` 解密失败 | 记录解密不可用或完整性不可验证，按冻结策略处理 |
| 原文验签失败或字段与 DB 不一致 | 记录无效/篡改，不能获得扩权 |
| 授权到期 | 独立于完整性状态处理，不能复用错误路径形成安全旁路 |
| 设备指纹不匹配 | 独立状态，不能以修改数据库字段规避 |

历史无原文记录只能通过合法原始 `.lic` 重新导入，或由厂家重新签发恢复；不能从数据库字段自动“补签”成可信授权。
