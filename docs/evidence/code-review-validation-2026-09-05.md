## 4. 已确认结论错误或影响夸大的条目

### 4.1 MED-16：SMTP 命令注入和 Bcc 外泄链路不成立

原报告称 Go 标准库 `net/smtp` 的 `Mail` 和 `Rcpt` 不校验 CR/LF。实际实现中，两者在发送 SMTP 命令前都会调用 `validateLine`；地址中包含 `\r` 或 `\n` 时立即返回错误。

项目的发送顺序是：

1. 调用 `client.Mail(cfg.From)`；
2. 逐个调用 `client.Rcpt(to)`；
3. 前两步成功后才调用 `client.Data()` 写入邮件正文。

因此，含换行的 From/To 会在 SMTP 信封阶段失败，不会进入正文发送阶段；在邮件头中拼接 `Bcc` 也不会自动增加 SMTP 信封收件人。原报告所述“注入 Bcc 导致邮件外泄”没有形成可利用闭环。

更准确的定性是：配置保存层的邮箱格式校验过弱，可能允许保存无效地址并导致发送失败。建议复用严格邮箱格式校验并显式拒绝控制字符，但不应继续按已证实的邮件外泄漏洞描述。

### 4.2 MED-31：过期授权不会替换当前有效授权

授权导入服务在写入数据库和更新内存状态前，会依次执行：

1. 文件解析；
2. Ed25519 签名验证；
3. Payload 解析；
4. 到期检查；
5. 主机指纹检查；
6. 产品形态绑定检查；
7. 加密授权原文并写入数据库。

已到期授权会在第 4 步直接返回错误，不会替换当前有效授权。代码中存在 `TestServiceImportExpiredRejected` 回归测试。

前端缺少二次确认可以作为交互风险保留，但原报告关于“误选过期授权会立即替换有效授权并导致全系统进入 423”的后果描述不成立。

### 4.3 MED-23：建议的校验方式不能证明离线包真实性

原报告正确指出“包内哈希可被篡改者同步重算”，但修复建议又要求校验包内 `manifest.files` 或可与安装包一同被替换的旁车 SHA-256。若安装包和哈希文件来自同一不可信渠道，这类校验只能发现偶发损坏，无法抵御主动篡改。

若目标是验证发布包真实性，应采用以下任一可信链路：

- 使用发布私钥对清单或制品签名，安装端内置或预配置可信公钥并在解压、执行前验签；
- 从独立且经过认证的渠道获取期望哈希；
- 使用具备签名和身份验证能力的制品分发系统。

因此，该条问题方向可以保留，但修复建议需要重新设计。

### 4.4 HIGH-14：攻击者范围描述过宽

安装脚本通常将 `runtime/hostctl` 设置为 UID 1000 所有、权限 `755`；此时不是所有本地用户都能写入标志文件。只有 UID 1000 对应非预期本地用户，或者 `chown` 失败后目录退化为 `1777` 等情况下，普通用户才具备写入条件。

执行脚本确实没有验证标志文件属主、目录权限或请求真实性，因此问题应保留，但建议改写为带条件的权限边界问题：

> 当 hostctl 目录所有权错误或退化为全员可写时，能够写入该目录的本地用户可构造合法 JSON 标志文件，由 root 执行 reboot、shutdown 或 factory_reset。

## 5. 当前仍能确认成立的重点问题

### 5.1 HIGH-5：共享引擎重建先销毁旧实例

`getEngine` 在新引擎初始化成功前，仍会取消旧实例轮询并关闭旧 Valkey 连接。随后若 `e.init(g)` 失败，代码把 `engineInst` 置为 `nil`。因此原报告指出的“先拆旧、后建新”核心问题仍存在。

建议采用以下切换顺序：

1. 在不修改全局旧实例的情况下完整构建新实例；
2. 验证新实例必需组件均已初始化；
3. 原子替换共享指针；
4. 替换成功后再停止并关闭旧实例。

还需要补充失败重载和并发在途请求场景的测试。

### 5.2 HIGH-7：超过 1 MiB 的请求体跳过 API 请求检测管线

`preserveRequestBody` 在已知 `Content-Length` 超过 1 MiB，或者流式读取超过 1 MiB 时返回 `nil`。`runAPIProtection` 收到 `nil` 后直接 fail-open 返回，不进入统一 API 请求检测管线，当前分支也没有记录跳过原因或安全事件。

该结论应限定为“API 动态防护请求相位被跳过”，不能扩大为所有 Coraza/CRS WAF 防护均被绕过。
