### 1.4 统计与噪声口径（冻结）

- 时延：curl `time_total`（客户端视角端到端），最近秩 p50/p95/p99；每档 ≥3 轮，报**中位数 + 三轮极差**；
- 轮间 p95 极差 > 30% 标「噪声告警」并原样给三轮值，不取平均掩盖；
- CPU：`docker stats --no-stream` 采样窗口内 ×3 取均值（网关容器），增量对照档 0 同窗口；
- RSS：档 3 每 30 s `docker stats` 采网关 MemUsage，绘首末/峰值；
- 污染剔除：仅剔除「采样器自身错误（000/连接失败）」并如实计数；429/5xx 一律计入分布不剔除（过载臂除外，其形态本身是断言对象）；
- 分母：所有比率以同轮同窗口对照臂为分母，不跨日比。

### 3.0 语料口径说明（先于数据，务必先读）

- **API 臂上游响应为 testorigin 404**：WAF 臂（A1/A2/A3）与 GraphQL 臂（G1）使用合成前缀路径，testorigin 无对应业务路由，返回 `404 page not found`（响应头 `X-Wdsp-Origin-Mark: jiuzhang-test-origin` + `Via: 1.1 Caddy` 实证请求**走完整管线 + 反代 + 上游处理**，非网关本地短路；档 0 与档 1 同臂路径一致）。管线在 OBSERVE 下对这类端点照常观测：档 3 期间 43 万请求全部产生运行时事件（§3.6），档 2 模型/schema 校验与 GraphQL 代价评估经事件与覆盖记录证实执行（§2）。因此**档间差值 = 管线/模块开销增量**，门槛 2/3 的增量语义成立；绝对时延口径 = 网关管线 + 反代 + 上游 404 处理（比真实业务上游偏快，绝对值不代表生产业务延迟）。
- **样本全部 `bad=0`**（无 000/429/5xx 污染）；404 按 §1.4 口径不计 bad（上游合法响应）。
- 写臂 429 规避有效：20 前缀轮换下三轮零 429。
- go 臂（R1/I1/I2/I3）为长连接复用客户端口径；curl 臂（W0/A/G/M1）为每请求新建连接口径——两口径不可互比，仅同臂跨档可比（§1.2 已冻结）。
- 轮间 p95 极差 >30% 的臂按 §1.4 标「⚠噪声」。

- 过载臂形态 = **体面降级**：延迟膨胀 + 发生器侧背压丢弃，网关无错误响应、RSS 621.7→619.9 MiB 平稳；过载后采样网关 CPU 回落至 40%，无残留积压性 CPU 占用。

## 6. 已知口径问题根因分析与改进建议

### 6.1 S7 冒烟「签名链 ~9.3 ms」根因拆分（本批专项，四臂对照坐实）

S7 冒烟记录签名请求链 p50≈9.3 ms，需回答「MID 验签是否吃掉了 2 ms p99 预算」。本批同环境四臂对照（全部 keep-alive Go 客户端口径，n=300×3，三轮中位 p50）：

| 臂 | 形态 | p50 | 差分解读 |
|---|---|---|---|
| I1' mid-observe.local 未签名 | WAF Off 宿主基线 | 1.17 ms | 反代+管线骨架地板 |
| I1 mid-observe.local 签名 OBSERVE | +MID 验签+重放写 | 1.33 ms | **MID 增量 ≈ +0.16 ms**（p99 4.26 vs 3.78） |
| I3 sf-s5.local 未签名 | WAF On（CRS 全规则集）无 MID | 8.64 ms | **CRS 评估 ≈ +7.4 ms（主导项）** |
| I2 mid-protect.local 签名 PROTECT | WAF On + MID PROTECT | 8.81 ms | MID 相对 WAF 基线仅 +0.2 ms；复现 S7 的 9 ms 档 |

CPU 侧互证（§3.5）：mid-uns 7.4% vs mid-sig 8.7%（Δ1.3 pp ≈ 0.17 ms/请求，与时延差一致）；waf-ping 43.5%（CRS 主导）。
**结论：9 ms 档 ≈97% 来自 CRS WAF 评估开销；MID 验签自身远低于 2 ms p99 预算（S7 单测锚定口径成立）。** 改进建议（只建议不动代码）：① 性能报告口径应区分「WAF On/Off 宿主」双基线，避免把 CRS 开销误记到新能力头上；② 若未来业务要求 WAF On 路径 p99 进一步压缩，可评审 CRS 规则集裁剪/并行化，属独立优化项。

### 6.2 gRPC 深检增量

R1（OBSERVE 深检，描述符加载）p50 11.02 ms vs R1'（同宿主无描述符对照）p50 9.90 ms：**深检增量 ≈ +1 ms**；h2c 传输+proto 编解码地板 ~9 ms 主导。CPU 侧 grpc-nd（85.3%）反高于 grpc（56.7%）——深检路径吞吐略低、单请求 CPU 略高但总窗更低，差异方向不一致即噪声主导，如实登记。

### 6.3 事件管线容量边界（档 3 实测）

collector 容量 ≈1,000 行/s（2000 行/批 × 2 s 轮询，§11.8/W20/W22 设计参数），A1 臂 1,809/s 到达下持续饱和。架构行为符合设计（文件缓冲+断点追平+幂等），但本环境下「API 事件全量入库」的持续吞吐上限 ≈1,000 事件/s——**若生产目标 RPS 高于此且要求事件零滞后，需评审 collector 批量参数或入库通道**（改进建议，记录不改动）。

### 6.4 本批工具缺陷实录（修正前后数据均留档）

1. `rpsload` 首轮相对睡眠节拍在 macOS/Rosetta 下仅达 1,433 RPS（sleep 粒度 ~1 ms）；改绝对时刻表+batch=4 后 600,000 节拍精确、达成 1,809 RPS（背压 dropped 9.5% 如实计数）。首轮数据留 `t3/`，修正后数据在 `t3b/`。
2. `s8-perf-stats.py` 初版按固定列序解析 go CSV，与 `rpsload` 实际输出（`seq,start_unix_ms,duration_ms,status,error`）错位；改按表头名定位列后复算，全部读数以复算为准。
