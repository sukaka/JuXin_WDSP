## 4. 共同约束

### 4.1 安全、兼容与事实边界

1. 先读根目录 AGENTS.md、当前任务书涉及的设计与实现；不复制竞品代码、页面、接口、数据结构和文案。
2. 复用现有认证、权限、CSRF、审计、配置编译、发布、节点确认和回退。配置保存、审核完成与节点实际生效须分别表示。
3. 原有防护先后关系保持不变。Bot 是明确新增步骤，新增位置及内部挑战端点的边界由 P1-02 冻结，须补真实 Caddy/Coraza 集成测试并同步架构文档。
4. Agent 镜像采集是被动观测，不能宣称其阻断了原始业务请求。Agent 采集、网关反向代理协议支持、APM 应用探针是三个独立维度。
5. Request ID、Trace ID、客户端指纹和未验证 JWT 都不是授权凭据。所有用户输入、外部流量和采集记录均为不可信数据。
6. 不把真实 Token、Cookie、私钥、密码、生产请求正文、SQL 字面值或个人身份信息提交到 Git 或写入证据。使用自建合成业务，脱敏必须发生在出主机及持久化之前。
7. 默认关闭新增主动处置和新增采集入口。能力不足、存储不可用、样本缺失时返回明确状态；不能以空数组、零值图表或绿色“正常”掩盖故障。
8. 第三方依赖与镜像锁定具体版本，多架构按架构锁定 digest；新增依赖记录来源和许可证。官方文档中的 `latest` 路径不构成部署版本选择。
9. 单元、接口、真实协议集成、关键页面 E2E 按变更补齐。模拟 Kubernetes、伪造 Trace、浏览器 Mock 响应、修改源码的编译 shim 均不能代替交付环境证据。

### 4.2 统一字段与状态

| 对象 | 统一规则 |
|---|---|
| 构建与配置 | build identity、源文件清单哈希、镜像 digest、规则/模型版本、发布批次、执行节点实际 ACK；不填写最新草稿冒充有效版本 |
| 关联 | application_id、request_id、gateway_node、时间范围及来源；Trace 匹配必须验证上下文，不能只按时间相近归为同一次请求 |
| 数据质量 | 区分数据来源、采集能力、存储健康、最后采集/入库时间、截断、缺失与不支持；未知值用 null 或明确 UNKNOWN |
| 决策 | 复用 P0 final_decision；API final_action 独立保留，采集端不能伪造网关执行结果 |
| 身份 | 复用 verification_status 与 verified_principal_id；挑战结果独立保存，不给 JWT 或 principal 升级可信度 |
| 验收 | PASS / FAIL / SKIP / BLOCKED / NOT_RUN；强制项未执行、跳过或证据不匹配时，所属阶段不可通过 |
| 环境阻塞 | 人类可读 BLOCKED_ENV；机器记录为 status=BLOCKED、reason=ENVIRONMENT_UNAVAILABLE |

### 4.3 UI / UX 共同验收

继续使用现有九章控制台的组件、权限模型和视觉系统。关键页面具有加载、空数据、部分数据、无权限、请求失败、保存失败、发布失败与部分节点生效状态。不能只有 Toast，没有可恢复入口。

链接保留应用与时间上下文；返回列表保留筛选和分页。风险、可用性和状态不能仅用颜色表达；支持键盘、可见焦点、读屏名称和合理窄屏布局。安全正文、Header、SQL 与异常文本一律以经过脱敏的纯文本展示，不执行 HTML/脚本。

## 5. 建议执行顺序与阶段门槛

编号用于保持与竞品报告一致，实际先建立回归工具，再增加主动防护。不要将依赖关系理解为授权并行改动整个工作区。

| 阶段 | 工作 | 退出条件 |
|---|---|---|
| S0 | 核实 P0/P1 状态，冻结共享 schema、范围和测试环境 | 真实差距、文件清单、接口增量、协议矩阵与证据记录均可审查 |
| S1 | P1-04 的语料契约、回放适配器和改动前基线 | 正常/攻击真值、执行数量、状态重置、构建绑定可验证；这不是 P1-04 最终验收 |
| S2 | P1-01 安全 + APM 真实演示与缺数据体验 | 事件到 Trace/SQL/异常闭环、无探针和失败状态、权限及任务耗时记录通过 |
| S3 | P1-02 Bot 策略、挑战与运营页面 | 挑战安全性、实际网关顺序、浏览器兼容、误挑战与业务损失指标通过 |
| S4 | P1-03 Agent 适配器、真实协议与 Kubernetes | 支持矩阵逐格有证据；断线缓存、重放、背压、重启和协议边界通过 |
| S5 | P1-04 持续门禁、模型/规则升级与回退演练 | 最终构建完成全量回归、候选对比、发布约束、真实回退并归档 |

## 6. 检查与交付纪律

实施时先核对模块依赖及测试环境。以下为已经存在的快速检查入口，新增包应加入对应命令；仅编写本任务包不运行应用测试。

```sh
(cd server && go test ./internal/apm ./internal/agents ./internal/apimodels -count=1)
(cd gateway/modules/jiuzhang_guard && go test -race ./... -count=1)
(cd gateway/dynamic_security && go test -race ./... -count=1)
(cd wdsp-agent && go test ./internal/httpsensor ./internal/events ./internal/buffer ./internal/transport -count=1)
(cd web && npm run typecheck)
(cd web && npm run lint)
(cd web && npm test)
(cd web && npm run build)
```

`server/tests/helper_test.go` 会重建测试数据库并使用特定 Valkey DB，先读取再运行，只连接独立测试环境。Go 的多层 `go.mod` 意味着在顶层模块运行 `go test ./...` 不自动覆盖全部嵌套模块；CI 必须显式枚举。用 `go test -json` 等原始结果核对实际执行数和 SKIP，不只看退出码。

每阶段交付：目的、文件清单、API/迁移差异、测试 ID 与结果、原始证据、已知限制、升级与回退、下一阶段依赖。工作区已有改动不得用 `git add .` 混入本任务。版本、提交和推送按实施时的用户授权和仓库规则处理；本次文档交付不触发应用版本升级。
